# Model

The data model, free of SwiftUI: the `ItemLibrary` protocol, `MarfaLibrary` over a Marfa server's working copy, and `Libraries`, which holds the host and the library the windows read. Views reach a library only through `ItemLibrary`: what a view needs to know about an item comes from the protocol, such as `hiddenPropertyKeys(of:)` (the keys an item's page already shows elsewhere, so Properties leaves them out) and `Item.source` (what made the item; nil where the library does not know). Before changing `Marfa/`, also read `MAPP/Model/Marfa/AGENTS.md`.

## Items and types

- MAPP names no item type of its own. What it shows of a type, its label, fields, parent and recommended values, comes from the server's catalogue (`Catalogue`). Code never tests for a type by its identifier, with one exception: `PageHeaderKind` walks up the parents to choose an item page's header (`core.event`: event, `core.entity.person`: person, `core.bookmark` and `core.media`: reading, anything else: the general page). `PageHeaderLead` and the `EventHeader`, `PersonHeader` and `ReadingHeader` it builds read fields by key, the contract's own names for those types, and nothing else about a type is special-cased.
- Change Type (`ItemLibrary.changeType`) changes an item's type in one queued edit, so it works offline. Marfa keeps the properties the new type does not declare, refuses a type whose required fields the item lacks, and reads the title and text from the new type's own keys without moving them (`device/body-retype`). So `TypeChange.plan` moves the title and the text into the new type's keys in the same edit: a title that the new type reads from the first line goes to the top of the text, and a first line becomes the title of a type that has one. Nothing is left only under a key the page no longer reads, written twice, or dropped: where the new type's title key already holds a different title, as another app may leave, that title stays the item's and the old one stays under its own key, which the sheet names as unused. `ItemLibrary.typeChangeOptions` offers the types at least one selected item can become: never a file type, never a type with no text for an item that has text, and never one where a value does not fit the new field. `ItemLibrary.typeChangePlan` decides for each item, and the items that can't become the chosen type are left as they are and named in a notice (`BatchSkips`); the change is one undo step. The sheet (`TypeChangeSheet`) asks for each required field the items lack and names the fields the new type does not use, which stay on the items. It runs once every open page has handed over its last edit (`changeTypeAfterSaving`), and closes only once the change is sent, so a change refused first keeps what was typed in it. A change the package refuses before queueing gives back the text values it carried, those typed in the sheet among them (`MarfaLibrary.unqueuedText`). Undo and Redo also wait for the open pages to hand over their last edit. An Undo or Redo pressed while the library is being brought up to date is held and made once the library is whole, if what it touches has not changed; otherwise it is not made, the person is told, and an Undo that was not made stays available, while a Redo that was not made cannot be put back (see `Marfa/AGENTS.md`). Undo puts back exactly the values the change replaced; if the item has changed since, its text or its type, Undo moves it back from what it is now as a new change, so what was typed is kept and no text is left under a key the old type does not read.
- Folders are facts on items, never places: MAPP syncs no folders and has no Folders section, Move To or New Folder.
- Which of a type's properties the item page shows, and whether Linked From sits on the page or in the inspector, is MAPP's own setting for each type (`PagePlacements`, one JSON value in the defaults), never written to Marfa. The inspector lists every property whatever is chosen, and what points at the item only as Linked From (its Relationships hold the links the item makes, never the `inverse:` groups), so an incoming link shows once wherever Linked From sits. With no choice, the page leaves out the type's `link_field` and an empty parent, and Linked From sits in the inspector, except for a person (`PageHeaderKind`) and a collection, whose page keeps it. A collection's Contents always stay on its page. A file has no page to customize, and the properties a header draws itself (an event's time, a person's job title, a reading's publisher) are not offered in Customize Page or the inspector's Show on Page (`PageCustomization`).

## Commands on a selection

- Every item command takes the whole selection, files too, and writes each item through the same queued, offline-safe edit it would use alone, in one undo step. The Swift SDK has no bulk call, so a large selection is one queued write for each item; the library's `submit` only queues, so the main thread is not held.
- An item a command can't change is skipped, never passed over silently: `BatchSkips` counts the skips by reason (gone, in the bin, can't be changed, a file, can't become the type, a collection that can't be filed in another, can't be filed, full of tags, can't go in the lane, a file that has no lane, not on the board), each with its own reason and `ItemLibrary.tellSkipped` tells them in one notice, titled "Some Items Were Skipped" where something did change and with the command's own title where nothing did. An item already as the command would leave it is not a skip. A command that is meaningless for the whole selection (nothing can take it) is dimmed or hidden by the menus, as before.
- Moving several items to Recently Deleted asks first, naming the count (`Browser.delete(asking:)`, `DetailsPresentation.deletion`, `DeleteConfirmation`); one item does not ask, since Undo puts it back. Delete moves only the live items of a selection and never erases: items already in Recently Deleted stay there, and a selection made only of them asks to erase them for good (the `notesToPurge` dialog, which says they are already in Recently Deleted and cannot be undone), or says why it can't while `canPurge` is false (`ItemLibrary.tellCannotPurge`). Delete Immediately and Recently Deleted use the same dialog.

## Version History

- Version History (the File and context menus, the More menu, the palette and the page's context menu) opens `VersionHistorySheet` for one item: its snapshots from the server (`ItemLibrary.history`), the chosen one beside the item as it is now, the version's other fields to read, and Restore. The command stays available offline and for a deleted item, and the sheet says plainly what it can't show. Restore waits for the open pages to hand over their last edit (`restoreVersionAfterSaving`) and its availability is judged on the item as it stands (`ItemLibrary.restoreCheck`), so an item changed or deleted elsewhere while the sheet is open is refused, not overwritten. See `Marfa/AGENTS.md`.

## This Marfa

- Settings > This Marfa shows and changes the connected server's own settings (`GET` and `PATCH /config`, needing `config.manage`): its name, how long deleted items stay (`trash_retention_days`) and the version windows and most versions kept per item. It is its own page, not part of Library, because it is about the server rather than this Mac's copy and has its own draft, save and failure states. The enforcement levers, the settings that need a receiver set up in the server's environment, audit, event-log and inbound retention, and unused-app retirement are left out on purpose.
- `InstanceSettingsModel` (held by `Libraries`, so a draft survives putting Settings away) keeps the draft beside the server's last answer. Nothing is sent until Save, and a save sends only the settings that differ, an emptied one as `null` so its default applies. Typed values are checked against the contract before sending (`InstanceSetting.entry(from:)`, `InstanceSettingsModel.problems`); the order of the version windows is checked in the app only when both are typed, otherwise the server judges it against its defaults and its reason is shown.
- A key cannot read the server's environment, so an unset field shows the documented default and says whoever runs the server may have set another. The documented default is shown, never compared with: an unset field is unknown. A value typed for an unset retention asks the person first unless nothing could keep more (zero days of trash, 36500 days, the largest version count), clearing a set retention asks unless nothing could keep less, and a set one asks when the new value keeps things for less time than the one held (zero days of trash is the longest, a zero version window the shortest). The words say it "may remove items sooner than the server’s current setting" (`InstanceWording.consequence`). A save reads the settings again first and sends nothing if a setting it would change has moved on the server; the page shows the new value and keeps what was typed. A refusal, an unreachable server or a missing permission never discards the draft. See `Marfa/AGENTS.md`.

## Writes the library cannot always make

- Deleting for good (`purge`) needs the server, so `ItemLibrary.canPurge` is true only while it can be reached, and the views dim the command until then. Saving, updating, renaming and deleting a view also need the server and are never queued, so `ItemLibrary.canEditViews` is true only while it can be reached, and the views dim those commands until then. An update made on a version changed elsewhere is refused and told, overwrites nothing, and the window goes back to the view as it is (`Browser.viewRefused`). A deleted view is gone for every app at once; there is no bin for views. Every other write goes to the copy's queue and can always be made.

## The sidebar

- The sidebar is in the manner of the Claude desktop app. A top block holds New (quick add) and Search (the palette), which act and take no selection, then Items, Sources and Collections (`SidebarPlan.destinations`). One block headed Views follows: Inbox, Recents and Favorites (`SidebarPlan.builtInViews`, places drawn there, not stored views), then the saved views. The Types block is last (`SidebarPlan.library` says which of Views and Types exist). Items includes files, and choosing it moves a window on the list to the gallery (`Browser.choose`), since Items, Sources and Collections stand under a row of "Make something new" chips (`Browser.offersNewItemChips`, `NewItemChips`) above the ordinary layout. The six places share one definition of their symbol, destination and count (`SidebarPlace.symbol`, `.item`, `.showsCount`), which the sidebar, Settings, the menu bar and the palette all read. Favorites remains visible when empty unless hidden in the sidebar layout. Recents lists the `ItemLibrary.recentLimit` items edited last, so its row has no count. Sources and Collections open indexes without disclosure toggles. Types has an Edit control, shown only while the pointer is over the heading, which opens a popover using the existing per-library visibility settings, with Show All. The block lists at most `SidebarPlan.shownTypeCount` (six) types with their subtypes, then a Show More row that becomes Show Less (`SidebarPlan.limited`). Whether Show More is open is the window's (`Browser.sidebarShowsAllTypes`), not the sidebar view's, because the window mounts its split view afresh when the place changes shape (list, gallery, index, Settings) and that drops a view's own state. `SidebarLayout.collapsed` remembers folded type rows. A type row that folds subtypes draws its chevron at the trailing edge, beside its count, and its subtypes are rows of the same list drawn indented (`SidebarPlan.typeRows`, `SidebarDisclosure`), since the system's outline disclosure always sits at the leading edge. The chevron of a type that opens its own list is a button of its own, and a click elsewhere on the row only opens the list; a group row, which has no list, folds on a click anywhere. The arrow keys fold and walk the selected type (`SidebarPlan.outcome(of:selected:)`). A thin guide leaves from under the parent's mark and bends into each subtype (`SidebarTypeRow.steps`). A subtype shows no mark of its own, so its name starts level with its parent's, unless Settings > Sidebar > Show Icons on Subtypes is on (`SidebarTypeRow.subtypeIconsKey`, off by default); top-level types and groups always keep theirs. A row is a label and a symbol, never a sentence.
- The foot row (`SidebarFoot`) holds the instance's name with a chevron and, under it, one line of sync state in words (`SyncFootLine`: Syncing with a spinner, Updated 2 minutes ago, N changes waiting to send, N changes need attention, Offline with the time or the waiting count, or Couldn’t sync with the reason as its tooltip), and the New Item button at its trailing end, sitting in the list's bottom safe area so the system shows a material only while rows pass beneath. The line shows only when a server is set (the sample library has none) and is read through a timeline that refreshes it once a minute (every second while changes wait). The name and chevron are one system `Menu` of Refresh (also File > Refresh with ⌘R and a palette entry, disabled unless `MarfaHost.canRefresh`), a divider, then Console (the server's console in the browser), Settings and Recently Deleted; Search is a row at the top of the sidebar as well as the palette (⇧⌘P and the Edit menu), and the sidebar's toolbar row keeps only the system's toggle. Recently Deleted uses the ordinary item layouts and the library's restore and purge operations. Sources lists source identifiers observed on active readable items, not a complete registry of connected sources. Views lists the instance's saved views (`ItemLibrary.views`, ordered by title) after the built-in views, in the Views block, and is absent when there are none or they cannot be read. A view's place (`SidebarItem.view`) lists what the copy holds of its items (`ItemSource.items(inView:)`), read when the place is shown and again after each change, so its row has no count. Each view is a place of its own in the layout (`SidebarPlace.view`, keyed by its item ID), so its row's menu hides that view alone (Hide from Sidebar) and also offers Hide Views from Sidebar for the section; rows drag to reorder within Views, and Settings > Sidebar lists every view with its own switch and order, so a hidden one comes back. Views stay in title order until one is moved; a new view follows the placed ones, a deleted one drops out of the plan, and the Views block is absent only once Inbox, Recents, Favorites and every saved view are off. The layout is MAPP's own and never written to Marfa. The command palette lists every view, hidden or not. A view that cannot be read keeps its last list and is told once. MAPP keeps no local saved-view store: New View (the View menu, the + on the Views heading and the palette) saves what the window shows as a view on the server (`ViewDraft`): its place, the table's filters, and the order and grouping of the layout showing (the list's or gallery's `NoteOrder`, the board's lanes, the timeline's date by day, or the table's options); a view's row menu renames or deletes it. A collection's view lists its members (`edge[in-collection] eq "<id>"`), in the view's own order, since a view cannot sort by an edge's position. Recents, Recently Deleted, the indexes and a single favorite cannot be saved, and what a view cannot hold (filters that would mix "and" with "or", a column a view cannot express, the list's date sections) is left out and named first. A new view's title or a view's new name stays in its sheet until the server takes it (`ViewTitleForm`), so a refusal can be tried again; a window that closes or changes library first gives the title back through `Notices.notKept`. A rename is based on the version the sheet opened on, so a rename made elsewhere meanwhile is refused, not overwritten. Opening a view applies its order and grouping, and shows each condition of its filter the table can show as the table's filters (`Browser.followView`, `ViewDraft.options(for:)`). Update View is offered only in the table, once its choices differ from the view's (`Browser.hasViewChanges`), and saves them at the version they were made on: the table's filters replace the conditions they showed, so a filter removed in the window is removed from the view, and conditions the table cannot show stay as they are and are named first. The layout a view was last shown in is kept on this Mac only (`savedViewLayouts`) and never written to Marfa. A layout kept under a name this version does not have, here or in a window's restored state, reads as the list (`ItemViewMode.init(from:)`).
- Collections are Marfa's: an item is a collection when its type plays the `container` role (`Catalogue.isCollection`), never by its type's name, and its members are the items with an `in-collection` edge to it, written at the member. The index lists the active collections by title (`ItemLibrary.collections`); it is flat, since a collection can't be in another (`Catalogue.canJoinCollection`, refused again in `linkProblem` and the relationship candidates). A collection's place lists its members in the order Marfa keeps: by each edge's `position` where it has one, then by title (`MarfaLibrary.membersInOrder`), so the list's order options are dimmed there and the table starts unsorted. Add to Collection and Remove from Collection take the whole selection, files too: an item that can't be a member (one in the bin, with a problem, or of a type a collection can't hold) is skipped and told (`ItemLibrary.collectionPlan`), and `ItemLibrary.collectionMembers` only decides whether the commands are offered; they write one edge for each item through the edge queue, with one undo for the batch that puts the positions back; adding appends positions only where the collection already uses them. An item made in quick add while a collection's place is shown joins that collection the same way once the library holds it (`Browser.finishNewItem`); a join the library refuses is told and leaves the item. `child-of` is hierarchy, shown as the item's parent and children, and has nothing to do with collections.
- `ItemLibrary.itemTypeCounts` lists the catalogue's types that directly hold active items, file types aside. A type counts only its own items, never its subtypes, and its place lists exactly those unless Include Subtypes is on for it (next item), so the count is the list's length (`MarfaItemIndex.activeByType`; only Files takes subtypes). Labels and icons come from the catalogue. A type's icon is `ItemType.icon`, the owner's choice or else its nearest ancestor's, drawn by the SDK's `TypeIcon`; the owner changes it from the sidebar row's Choose Icon menu (`TypeIconPicker`), which calls `ItemLibrary.setIcon` and needs `canChooseTypeIcons`. `MarfaLibrary` keeps the chosen icon until the working copy's catalogue shows that type with a different icon than it had at the choice (the chosen one, or one another app set). `ItemLibrary.pageLayout(of:)` (`ItemPageLayout`) is the one rule that chooses an item's page: an HTML file (or a `core.file.webpage`) opens in the sealed web page, never Quick Look, which fetches every picture the HTML points to; another file opens in its preview; an item that is not a file but has an HTML document attached (a file not in the bin whose `resource_kind` is `html`, as Readwise Reader keeps an article; the oldest of several) opens to that document under its own title and byline; every other item opens to its text. It reads only what the library holds, so the layout does not change while a file is fetched, and the inspector still shows the item itself. `WebPageView` shows the HTML in `SealedWebPage`, a web view with no network, no stored data, no WebRTC (a document-start script removes the interfaces in every frame, since WebKit has no public switch for the engine; `SealedWebPageEscapeTests` tries each frame and worker route with a datagram listener) and no bridge to the app beyond its pictures (below); links in the page do nothing. Only a Web Page runs its scripts; any other document runs none (`allowsContentJavaScript`). `WebPageItemPage` shows it as the item's page, and each document, a new version of the same file included, loads into a page of its own.
- Include Subtypes lists a type's subtypes' items with its own, as Obsidian's stack button does for a folder. It is offered only for a type with at least one subtype that holds items (`Browser.stackableType`), in the list's toolbar (`ListToolbar`), in the View menu and in the command palette, and is remembered for each type in the defaults (`IncludedSubtypes`, mirrored in `Browser.stackedTypes` so the views follow a change). What a list shows goes through `Browser.placeItems`, so the layouts on offer, a new item's following and the list agree. The type's count in the sidebar does not follow it, and nothing else about the place changes: search, a saved view and the other places list as before.
- Types nest by their identifiers below the vendor segment (`TypeNode.tree`): `aic.ticket.task` under Ticket, `aic.agent.session` under a group named Agent. A group of one gives way to its row; a nested row drops the words it repeats ("Session"). Siblings go by their branch's items, then label. A group, or a type with no items of its own, only folds open. Flat lists, such as the command palette and quick add's kinds (`ItemLibrary.creatableTypes`), tell two types with one label apart by their parent's, "Task (Ticket)" (`Catalogue.displayLabels`). A type whose last item goes has no row, a collection no longer active has no place, and a view deleted on the server has neither, so `Browser.placeRemoved` moves a window on any of them to All Items.
- `SidebarLayouts` keeps what the person hid, collapsed or moved, one `SidebarLayout` for each server (`Libraries.sidebarLayoutKey`). A place a layout does not mention, such as a new type, is shown after the placed ones. `SidebarPlan` is what the sidebar and Settings > Sidebar both read.

## Search

- Search runs in the working copy and never calls the server, so it works offline. `ItemLibrary.search(_:in:)` takes a `SearchScope` (everywhere, or the open place where `SearchScope.narrows` allows) and answers `SearchResults`; `Browser.searchesPlace` is the person's choice. A place is searched by the copy's own filters (`SearchFilters`, or `search(inView:)` for a saved view), so the app matches nothing itself. The most the copy lists is `SearchResults.limit`, and `isCapped` says more was found. The copy cuts its list before the items in the bin are dropped, so the notice counts the rows shown (`SearchResults.cappedCount`), not the limit.
- Each hit's excerpt is the copy's own (`SearchExcerpt`, read from its `<mark>` HTML). It is stamped with the version and modified date it was cut from and shown only while `describes` still holds, so an item edited after the search never shows old text.
- A copy that is filling or behind the server answers `.partial` or `.stale`. Both read as `isIncomplete`: the list says so, and an empty list says it is still looking, never that nothing matches. A search that found the copy incomplete runs again whenever the copy's fill report changes (never on a copy that stays stale, which would repeat it without end), so the notice follows the latest answer.
- A failed search tells the person and keeps only its own earlier results, for the same words and place; with none it shows nothing. Its notice follows how the copy stands now. `isPending` marks a search not yet answered, so an empty list then says nothing.
- Relevance is the order the copy ranked the results in (`SearchResults.items`), and the palette lists them in it. The list starts a search on Relevance (`Browser.ordersByRelevance`): one section, no date groups. The gallery and the table start on their own sorts and use relevance only once it is picked there (Sort By, or a palette command). Relevance never changes the stored sort (`OrderKey.sort`); picking another sort leaves relevance, and the search ending (`Browser.relevanceChoice` is forgotten) gives the person's own sort back. The board sorts each lane's cards by title and the timeline its days by date, with no choice of sort. The fake copy has no search, so the sample library lists nothing for a query; tests drive `MarfaLibrary` through `FakeItemSource`.

## Relationship names

- Both ends of a link are named by Marfa: `EdgeType.label` on the source end and `EdgeType.reverseLabel` on the target end (`EdgeTypeInfo.label(atTarget:)`). MAPP names no relationship and shows these as they come, never as localized keys or reworded. When the two are equal the relation is two-way (`EdgeTypeInfo.isTwoWay`), and an item's outgoing and incoming links form one list.
- A group of links in the inspector (a relationship, or the links in the item's content) draws its first `LinkLimit.limit` rows and ends with "Show N More", which shows the rest. The window keeps which groups are shown in full, for each item and group (`DetailsPresentation.expandedLinks`). A relationship group's links are ordered by title, then ID, so the same ones come first each time; the links in the item's content keep the order the item's edges are held in. A link to an item in Recently Deleted is marked "Deleted" and still opens, in Recently Deleted (`Browser.place(listing:)`); a link to an item the library does not hold is "Item not found", keeps its ID so it can be removed, and opens nothing.

## The table

- The table view (`ItemTableLayout`) is worked out from the items a place shows, never stored: a column for each field their types declare, not the title or the text, leading with status, priority and assignee, then where each item is filed (the parent link, headed with Marfa's name for its child end), then the rest, and Edited. A field few items fill, and the quiet ones (notes, url, place, precision), start hidden. A mixed table's column holds one type's field, so a cell offers its own type's values.
- A status sorts, groups and colors by its tone (`StatusTone`), so every type's word for it reads alike; the page header's ring follows the same tone (`PageHeader.Mark`). A place with statuses starts grouped by status with finished work folded, and ordered by priority, highest first. Empty cells sort last either way.
- What the person chooses (grouping, sort, filters, folded groups) is the window's, for each place (`Browser.tableOptions`); which columns show, in what order and width, is kept for each place in the defaults.
- What a place's table shows (`ItemTableContent`) and the list's sections are worked out once for the window and shared (`Browser.tableContent(in:)`, `Browser.sections(in:order:now:)`), until the library's `contentRevision`, the items listed, the place's options, the order or the day change; a selection never makes them again. A view, a command or the palette asks the browser and never builds an `ItemTableContent` itself, and a new `ItemLibrary` must bump `contentRevision` whenever its items or catalogue change. A table's sort reads each row's values once, then compares (`ItemTableLayout.sorted`). `Cost` marks the work that runs as a person moves around (signposts under the `performance` category, and a tally in Debug builds), which the `Measure` plan reads.
- The table draws a page of its rows, not all of them (`TablePaging`, `ItemTablePaging.swift`): the first `TablePageSize` rows (25, 50, 100 or 200; 50 to start), then a Load More row that adds another page, and, when grouped, a page and a Load More row for each group. The library holds every item and sorting, filtering and grouping need every row, so paging is only what the table draws: `ItemTableContent` holds all rows, the header's count and a group's count are of all of them, and a page never makes the content again (the page size is left out of the content's key). The page size is part of the place's `ItemTableOptions` and is the window's, like the sort; a saved view has no field for it (`ViewDraft` never reads or writes it), so a saved view keeps the place's choice. How many pages are loaded is `Browser.tablePaging`, read as one page whenever the place, the search, the order, the filters, the grouping or the page size differ from when the pages were asked for (`TablePagingKey`); an edit to an item or a folded group does not start it again. A selection the table holds beyond the loaded rows (Back, a link, a new item) loads the pages that show it (`Browser.revealSelectionInTable`); Select All and the arrow keys act on the loaded rows, and Delete on the selection only. Load More is a button row (`ItemTableLoadMore`) and a palette command (`ViewOptionCommands`). The list and the gallery are not paged: the list is a lazy `List`, and the gallery's cost does not grow with the item count enough to feel.

## Remote pictures

- A picture at a web address in a note is fetched only by `PictureFetcher`, only when `WebPictures.answer` says so, and only for the editor page's `pictures` message (`MAPP/Editor/PictureRequests.swift`) or a sealed web page's picture scheme (`SealedPictures`). Nothing else in the app fetches one. Settings has Remote Pictures: Ask (the default), Always or Never, in defaults under `RemotePictureSetting.key`, read at each question. Ask leaves each picture as a card until the person loads it; Always loads without asking only a picture in an item in the feed tier (`Item.tier == .feed`, the Inbox), which is where connectors write and captures land, and also where a note the person makes while the Inbox is selected lands (`MarfaLibrary.createItem`, `place == .inbox`), so Always loads that note's pictures too; it asks in the library tier as Ask does, since the website would learn the person opened one of their own notes there. `Item.source` cannot tell the two apart: Marfa stamps every item with the source of the key that wrote it, so a note written in MAPP has a source too (`MarfaMapping` maps only an empty source to nil); Never fetches nothing, even for a picture the person chose. A file attached to the item that was saved from the same address (`source_url`, see `Editor/AGENTS.md`) replaces the address under every setting and ask, with no request, and `WebPictures.answer` is not reached for it; with it binned or removed the setting answers again. A picture already in the cache shows under every setting, Never included, since showing it asks nothing of the website, and one loaded in the feed keeps showing after its item moves to the library. Printing and export use the cache or a saved file only, and ask the website for nothing.
- A document in the sealed web page reaches its pictures the same way. Before it is shown, `SealedPictureRewrite` points each `img` at a web address (its `src`, or its `data-src` where it has none) at the editor's URL for a picture saved in an item (`EmbeddedFiles.pictureURL(for:version:savedIn:)`, the `mapp-embed:` scheme), the one address the seal lets through, and drops every `srcset`, on an `img` or a `<source>`. `SealedPictures` answers that scheme for the page's own item, and only for the addresses its rewrite found: a saved picture first, then `WebPictures.answer`, as for a note; anything else is an empty picture that keeps its place. While pictures wait under Ask, `WebPageItemPage` shows the count above the page, and loading them redraws each picture in place (`SealedWebPage.redrawPictures`, run in a content world of its own, so it works with the page's scripts off). The page itself fetches nothing.
- `PictureFetcher` takes an `https` address only, by `GET` only, in an ephemeral `URLSession` with no cookies, credentials or cache, no referrer and one fixed `User-Agent`. `PictureAddressPolicy` checks the address before the first request and at every redirect: no sign-in in the address, no single-label name, `localhost`, `.local` or `.localhost` name, and no literal or resolved address that is private, loopback, link-local, unique-local, multicast, reserved or an IPv4-mapped or NAT64 form of one (`IPAddress.isPublic`); a name with any such address among its answers is refused. At most four redirects are followed, 25 MiB is taken (counted while the bytes arrive, as well as from `Content-Length`) and 30 seconds, which start with the first lookup of the name: a lookup is given at most 10 of them and runs on queues of its own (`getaddrinfo` blocks), never on Swift's cooperative pool. The IPv4 inside a mapped (`::ffff:a.b.c.d`), translated (`::ffff:0:a.b.c.d`) or NAT64 form decides. The session answers only the check of the server's certificate: a request for a client certificate or a sign-in is rejected (`rejectProtectionSpace`), so no identity or password is offered to a website. The kind is told by the first bytes (`PictureFormat`: PNG, JPEG, GIF, WebP, HEIC, AVIF), never by the server's header, and never SVG. A picture one pixel wide or high is refused, as is one over 100 million pixels. Each refusal is a `PictureFailure`, whose text the card shows.
- **Known limit: DNS rebinding.** The policy resolves the name itself, but `URLSession` resolves it again when it connects, so a server that answers the check with a public address and the connection with a private one is not stopped. Closing that gap means connecting to the address checked, which needs Network.framework with its own TLS and redirect handling. What is left is a GET that is saved to a file and shown only if it is a picture of a kind the system decodes, with no way for the page to read the response. Do not claim more than this in the interface or the docs.
- `PictureCache` keeps fetched pictures in the system caches folder, in a folder named for the bundle identifier, one folder per address (a hash of it), with the oldest-used removed first beyond 200 MiB. They go when the library is disconnected (`MarfaHost.disconnect`, as `MarfaSource.removeKeptCopies` does for files), and the system may clear them sooner. A fetch that is waiting or on its way at that moment keeps nothing: `PictureCache.generation` is read when the fetch is asked for, checked before it starts, checked again once the address has passed its check and before any folder is made or request sent (`PictureFetcher.fetch`'s `proceed`), and checked once more under the lock that `removeAll` takes, in `store`, which trims the cache only after it lets that lock go. `store` always consumes the fetched file, removing it if it keeps nothing, and the first use of a cache sweeps what an earlier run left in its `.incoming` folder.
- `PictureQueue` lets four fetches run at once, two for any one website, and holds the rest in order: a fetch waits for its turn and is not refused, and a website at its limit does not hold up another.
- Tests drive `PictureFetcher` through a stub `URLProtocol` (`MAPPTests/Pictures/PictureStub.swift`) and reach no network.

## Changing libraries and quitting

- `Libraries` owns the `MarfaHost` and the library the windows read: the host's `MarfaLibrary` while its copy is open. Its `mode` says what a window shows instead otherwise: with no server set (`unconfigured`), a page that asks the person to connect to their Marfa and opens Settings > Library; while a copy opens (`opening`), a wait; and when a set server's copy is not open (`failed`: a refused key, a copy that cannot be opened), a page that says so and points to Settings. There is no other library to fall back to.
- Before the host changes which library the windows read, and before the app quits, `Libraries.flushEditors` has every open page hand over its last edit (`EditorController.flushAll`), and the library keeps its writes on this Mac in the copy's queue (`ItemSource.queueSubmitted`). It never waits on the server, so quitting offline is not held up. Every window's unsaved titles are saved first, and a title still refused cancels the quit or the library change and names the item (see `MAPP/Editor/AGENTS.md`). Quitting waits a few seconds at most; a flush that fails or runs out of time cancels the quit, and the person is told why (a page given up on, a refused title, or a library still saving).
- A main window's `Browser` sits above the library, in `RootView`. A change of library resets the window (`Browser.adopt`: selection, place, search, the new item being followed, and the window's undo), since they name items the other library may not hold. `MainView` is made again for the new library, so the window's quick add draft has already gone to the clipboard as the old one went.
- New Item (the sidebar foot's button, or the toolbar's while the sidebar is hidden, ⌘N and the palette's New Item and New <Type>) opens quick add (`QuickAdd`, `Browser.openQuickAdd`), a panel in the middle of the window: its title and text, a file, or a title alone, as the kind keeps. Its footer holds the kind of item and a plus menu, then Cancel and Add. The plus attaches a file and adds the parent (chosen from a list that opens on the plus, so the library is searched only then) or any field the kind has that is not yet a chip (`QuickAdd.offeredChips`); a file item takes a parent but no field, since `addFile` takes no values. What was added shows as chips in a row above the footer's divider (`QuickAdd.shownChips`), each opening its own editor and, unless the field is required (`QuickAdd.isRemovable`), with a button that removes it and its value. A required field is always a chip, and a value or parent the draft holds shows as one too. The draft keeps its chips (`Draft.chips`), and changing the kind drops those the new kind cannot show. It never writes an empty item: adding needs a title, or one file for a file type, a value for every required field, and a parent the library still holds (`QuickAdd.canSave`); a parent it no longer holds shows as "Item not found" so it can be removed. Text the kind does not keep, such as a note's text after the kind changes to File, is never dropped: the panel keeps it in sight with a line saying so, and adding waits until it is removed or the kind changes back (`QuickAdd.holdsTextItCannotKeep`); so are files a file item cannot hold, more than one (`holdsFilesItCannotKeep`).
- Files reach quick add by Attach File in the plus menu, a drop on the panel or a paste (`QuickAdd.File`, which holds the file's security scope while any draft or new item names it, and refuses anything that is not a readable regular file). For a file type the same menu item, named Choose File, chooses the one file. The kind stays File: MAPP sends the media type the system gives the file and no type, and Marfa's core makes it the built-in file subtype that media type calls for (`MarfaEngine.mimeType(of:)`). For any other kind the files are attachments, shown as chips the person can remove. Each file is read from where it is at Add, never copied first; one gone by then is taken out of the draft, the person is told, and nothing is added.
- `Browser.saveQuickAdd` makes the item in one create (`ItemLibrary.createItem` with its properties, or `addFile` from the file's URL, under the chosen parent), so a required field is never set after the create. Then the panel closes and the item opens (`NewItem`, `finishNewItem`), when its library says it holds it, not when the create is sent; a note opens with the caret where it was in the panel (`PageCaret`). Attachments are attached after that, one at a time (`ItemLibrary.attach(file:to:)`); for a kind that keeps text their embeds go to the end of it through the editor's own saves (`Browser.newEmbeds`, `EditorController.append`), so they never race the person's typing. An attach that fails leaves the item and its text as they are and names the files not attached through `Notices`; a create refused later, or a window that closes or changes library first, names them too (`giveUpNewItem`). A create the library refuses leaves everything as typed, and the library tells the person why. The draft belongs to the window: Cancel, Escape or a click outside puts the panel away and keeps it, files included, and when the window closes, changes library or the app quits, a draft with anything in it (text, a file, a parent, a value or a chip) goes to the clipboard through `Notices.notKept`, its values and parent named after the text, with the reason and the names of any files not added (`QuickAdd.handOff`, `QuickAdd.Departure`). A file being added, and the title sent with it, are on their way already and are not handed off.

## Telling the person

- Everything the app tells the person in an alert goes through `Notices`, which the host makes and gives to every library it opens (`ItemLibrary.notices`): something a library could not do (`tell`), a change it could not keep (`notKept`), and an address that sends the key unencrypted. Each waits in order until one window in front shows it and the person answers, so a notice from a library the windows have left is still told, and a later one never replaces it. `Notices.show(in:copying:)` decides which window shows it, one at a time, released when that window answers or closes; the person's answer names the notice by its `id`. Changes not kept gather into one notice until it is shown, and its text goes to the clipboard the first time it is shown (`View.notices`) and is never written again; a change not kept after that waits in a notice of its own, so nothing on the clipboard is written over before the person answers. A quit waits for a change not kept that no window has shown, as when no window is open, and tells it in an alert of its own (`Notices.tellBeforeQuitting`). Add no other route. A notice can carry an `action` (`Notices.Action`), a way forward the alert offers as its default button beside Not Now, which the window showing it carries out (`View.notices(_:openSettings:)`); every other notice has the system's single OK. Only a key the server refuses has one: while the copy is open the windows keep showing the library, so that notice is the only sign, and its Open Settings goes to Settings > Library, where the person enters a new key or disconnects the library to start again. An item's window has no browser, so it opens a main window at that page.

## Code Review Rules

- **Named type.** Flag code that tests for an item type by its identifier, or gives one a label, field or behavior of its own, outside `PageHeaderKind`'s header choice. Flag an SF Symbol named for a type.
- **Folder as a place.** Flag a change that brings back a folder as a sidebar place, a move between folders, or a folder MAPP keeps or syncs itself.
- **Fallback library.** Flag a change that shows anything but the connect, waiting or failure page while no server's copy is open.
- **Unflushed switch.** Flag a change of library or a quit that does not first flush the open pages (`Libraries.flushEditors`), or that goes ahead when the flush fails. A window close waits for its editor's flush the same way (`EditorCloseDelegate`).
