# Editor host

The Swift side of the note editor: the web view, the controller that drives the page, the bridge's messages, the `mapp-embed:` scheme, and printing. The page's own source is in `editor/`; read `editor/AGENTS.md` before changing the bridge.

## Web view

- Use AppKit's `WKWebView` in an `NSViewRepresentable`, not SwiftUI's `WebView` and `WebPage`. An editor needs what they do not offer: printing, filtering WebKit's context menu rather than replacing it, routing Undo to the page's own history, dropped files, and focus. Revisit only when Apple makes editing, printing, and the scroll edge public in them.
- `WebViewChrome.swift` sets two WebKit settings that are not public API, as Apple's own `WebView` does: a clear background (`drawsBackground`) and the automatic content inset background fill (`usesAutomaticContentInsetBackgroundFill`), under which the page runs beneath the toolbar. Each is set only while WebKit responds to its selector, and the page must still work without it: it then keeps its own background and stops below the toolbar. Whether the second also makes the system draw a soft edge over the page has not been seen on a real window, and nothing relies on it. Add another private WebKit setting only on the same terms: Apple's own `WebView` uses it, it is guarded the same way, and the page works without it.
- The window's toolbar draws no background (`MAPPApp`), and the page scrolls in WebKit rather than in a SwiftUI scroll view, so the app does not rely on the system's scroll edge effect reaching the page. The system's own edge is a hard one: a nearly opaque, blurred band with a straight lower edge and a hairline. Its public API is `scrollEdgeEffectStyle(_:for:)` for a SwiftUI scroll view and `NSScrollEdgeEffectStyle` for a titlebar or split view item accessory; nothing public reaches a web view's scroll edge, and WebKit's own is private. `NotePage` therefore draws `ToolbarBand`, the app's own signal that content is under the toolbar and a copy of that look: `.bar` material at `ToolbarBand.strength` (0.9) over exactly the toolbar's height, ending hard with no fade, and a hairline of the system's separator color, one physical pixel tall. It is shown only while `EditorController.isContentUnderToolbar` is true (the page reports it when it has scrolled, `contentUnderToolbar`), so there is none at the top or on a page too short to scroll. The item window, whose toolbar keeps its own background, turns it off (`backsToolbar`). It sits in the page's view, never changes its layout, and takes no clicks. The list column gets the same band through `bandsToolbar()`, which shows it once `onScrollGeometryChange` reports the list scrolled beneath the toolbar and always hides the system's edge for that list so only one draws. Settings > Appearance > Toolbar > Show Toolbar Background When Scrolling (`InterfaceKey.showsPageToolbarBackground`, on by default, read by `NotePage`) turns the band off on a note's or item's page only; the list always keeps its band, since a list without one is hard to read. If the system's edge is ever seen to draw over the page too, the band is the thing to remove.
- The window's toolbar shows the title of the note on the page once the page's header has scrolled away (`EditorController.isHeaderScrolledAway`), as `ScrolledItemTitle`, unless Settings > Appearance > Toolbar > Show Title When Scrolling (`InterfaceKey.showsScrolledTitle`, on by default) is off. The title is fixed to the width of its own text, up to `ScrolledItemTitle.widest`, never to the width the toolbar offers it: an item that reports the width it was last offered shows a title cut to "14…" the first time it appears.
- The navigation delegate allows only the page itself and `mapp-embed:` requests. Keep every other navigation cancelled.
- The page keeps ⌘[ and ⌘] while it has the keyboard (`EditorController.isFocused`): it outdents and indents a list item and moves between table cells with them. The View menu's Back and Forward (`AppCommands`) give those keys up then and keep them for the list, the sidebar and the gallery.
- The controller reports native responder and key-window changes through `window.editor.setHostActive`. Inkkit owns selection painting; the bridge only reports whether the web view has the keyboard in the key window and never changes focus or history to recolor a selection.
- A window makes its editor once: the view keeps an `EditorSlot` in `@State` and reads the editor from it in `body`. SwiftUI makes a view's value again each time its parent updates and keeps only the state it stored first, so an editor made in a view's initializer builds a web view and loads the page in a process of its own, only to be thrown away.

## Embedded files

- `ItemLibrary.openEmbeddedFile(_:in:waiting:)` in `EmbeddedFiles.swift` is the one place an embed becomes a file: the `mapp-embed:` scheme, the page's images for printing, Open and Show in Finder, and the gallery's picture for a note all ask it. Do not resolve an embed anywhere else, and run no link or embed rule of MAPP's own. Marfa's core binds each embed to its file item when the text is saved (`Item.boundEmbeds`, from the package's `links(in:)`), and lists each embed by its text as the note holds it, such as `![[photo.png|400]]`. The page sends that same text (InkKit's `FileReference.raw`), and the library matches the two exactly, so the text also says which kind of embed it is. An embed the core does not list, such as one of a note, is not a file, and one bound to a file in the bin is treated as a link to a binned note is: both show as missing. The library fetches the bound item's file (`fileURL(of:)`) and opens it with `OpenFile.open(_:inside:)`.
- An embed is waited on, for at most `EditorController.embedWait`, only while its text is not yet in what the library has read: while the note has a save the copy has not read again (`ItemLibrary.hasUnreadSave`; a save the source refuses to take, as it has closed, is never waited on, since it gets no answer), or before the page's save reaches the library. Once the save is read, an embed with no binding is missing at once. A file that can't be had now (the server can't be reached, there's no room, more than one file has the name) answers `unavailable` with the reason, and the page shows an error card with the reason and Inkkit's retry rather than a missing one.
- `EditorController.watchEmbeds` tells the page when the pictures of the note on the page may differ, as `watchLinks` does for links. It tracks `ItemLibrary.embedStates(of:)` (each embed's binding, and the title, bin state and version of the file it names), waits for the changes to pause, compares with the states last told, and calls the page's `embedsChanged` with just the texts that differ; the page then asks again for those, through Inkkit's `refreshReferences`. So a file arriving, renamed or removed redraws its embeds and nothing else, and a note with hundreds of embeds asks nothing again. Showing a picture never rewrites the note. Known limit: a connection that returns after an offline spell does not redraw an embed that showed an error card; its retry does, and so does any later change.
- `OpenFile` opens the file with `O_NOFOLLOW_ANY` and keeps it only if the descriptor's own path (`F_GETPATH`) is an ordinary file inside the directory it was looked for in, under no name starting with a dot. Everything the page is told or served comes from that descriptor, so a directory changed after the check cannot put another file behind it. Never reopen by path after the check.
- A picture at a web address is asked of the app through the `pictures` message handler (`PictureRequests`), not `embeds`, and served from the `mapp-embed://picture/?address=…&v=…` host of the same scheme handler: `EmbeddedFiles.serve` opens the cached file for that address (`WebPictures.openKept`) through `OpenFile`, inside the cache's folder, so what is served is a file the cache holds and never a fetch. `PictureRequests.reply` is the one place the page's question becomes `WebPictures.answer`, and it asks `ItemLibrary.openSavedPicture` first: a file attached to the item (an `attached-to` edge) whose `source_url` is the same address (`SavedPictures.same`: scheme and host in any case, default port and fragment ignored, path and query exactly) is the picture, whatever the setting and the ask, with no request to the website. The match names no type. It goes through the embed route's `open`, so a file is fetched if this Mac does not hold it and only an image counts; one in the bin is skipped, and of several the oldest is tried first. A matching file that can't be had now answers `refused` with `retry`, never the website. The reply's URL is `mapp-embed://picture/?address=…&item=…&f=…`, and `EmbeddedFiles.serve` looks the file up again for it (`openSaved`, never the cache), so a file binned since is a 404, and so is a URL with an `item` field that names no file (empty, or not valid percent-encoding). A portable export reads the file's bytes, within the same `largestExport`. `watchEmbeds` also tracks `ItemLibrary.savedPictureStates(of:)` and, when such a file arrives, changes, is binned or goes, calls the page's `savedPicturesChanged` with the `source_url` of each file that differs, so the page asks again about the pictures at those addresses only (compared as `SavedPictures.same` compares them, in `sameAddress`), not one being chosen, and not a refusal at any other address. Otherwise it passes whether the item is in the feed tier (`Item.tier`, wired in by `EditorController`), which Always needs and `Item.source` cannot say, since every item has one, and drops an answer if the note on the page changed meanwhile. Printing and a portable export reach a picture's bytes through the page's `exportImage`, which asks with `cached` and `export`, so `PrintDocumentRenderer` and an export read the cache or a saved file and ask the website for nothing (`reply` answers the bytes, at most `PictureRequests.largestExport`). The Remote Pictures setting is read at each question; `EditorController` tells the page with `picturesChanged` when it changes. How a picture is fetched and kept is in `Model/AGENTS.md`.
- The copy of a file that MAPP keeps on this Mac is read-only (`MarfaSource.keptCopy`), so an app that Open hands it to offers to duplicate it rather than save over Marfa's file.
- The scheme handler streams the file in pieces and answers byte ranges, which WebKit's media playback needs.
- `EmbeddedFiles.opens` decides what Open may hand to another app. It never hands over a file that might run (a program, a script, a web page, a link file, anything marked executable, or a kind it cannot tell); such a file is shown in the Finder instead.

## Saving

- Each load of a note gets a generation, and each edit reports the generation and the version of the text it was typed on (`EditorController`). Never save an edit without its version, and never let an edit from an earlier generation save into the note now on the page.
- A note whose text the library cannot give (`body(of:)` is nil) is not opened. Once the note before it has handed over its last edit, the page is emptied and made read-only under a generation no note owns (`clearPage`), so the text of the note just left never shows under another item's header and nothing typed there reaches any note.
- A failed capture of the page's last edit cancels quitting, closing the window, or changing libraries, and the person is told. A page that cannot hand over its edit within `EditorController.flushLimit` (busy, or stuck in a composition) is given up on: the library's `notices.notKept` tells the person that the most recent typing could not be saved, with no text, since the page reports each change as it is made and what it last reported is already saved. The next flush goes ahead without the page, until the page reports a change again. Outside text that reloads the note during a flush does not stop it, since the note is still the one being left, and the flush still asks the page for the generation it began on: the page puts a reload off while the person composes, so it can still hold that generation's text, and a page that has moved past it reported that text as it moved and answers nothing (`flush` in `editor/src/editor.ts`). A flush whose note was replaced on the page stops, and the person is told why. A page whose process ended reported every change as it was made, so it never holds up a flush while it reloads.
- Images go into a note through `library.attach(_:to:)`, and the page inserts the returned links with `insertImages`. The editor then saves it like typing. One image that can't be read or attached never stops the others: the rest are placed, and each one that wasn't is named to the person (`Some Images Weren’t Attached`, or `Can’t Attach Images` where none was). So is one attached after the note left the page, since it is among the note's attachments but not in its text. Each keeps a name distinct among the item's attachments.
- Files attached in quick add are attached after the item is made, and their embeds wait in `EditorController.pendingEmbeds` until the page shows that item, editable and ready; the page then adds them after the last block of the text with Inkkit's `appendImages`, leaving the caret where it was, and saves them like typing. They stay waiting until the page says it wrote them: it takes none while the note is edited as source or composing, and they are sent again when the page next reports its state outside source editing. A refusal that waiting cannot change, such as a note ending in an open code fence, or a failure of the page's defensive source-preservation check, tells the person which files are attached but not in the text (`notInText`). So does a window that goes while embeds still wait. The files stay attached to the item and the note's text is untouched.

## Header

- The header is drawn in the page (see `editor/AGENTS.md`). `MAPP/Views/ItemPageHeader.swift` carries out its events: it builds the header's data (the byline, the `PropertyRow`s and the `LinkedItem`s from `MAPP/Model/Items/PropertyRow.swift`) and saves the title through `setItemProperty` on Return or when the title loses focus. Title typing is undone by WebKit's own steps. `openItem` opens the linked item in the same way a link in the text does. A refused status or a refused Remove Parent sets a flag on the item's draft (`DetailsPresentation`), which the header shows as its own message; nothing is dropped silently.
- The editor follows what the header reads (`EditorController.showHeader`) and builds it again only when that changes, so the header reads only what it shows: the item's own record, the records of the items it links to or is linked from, the catalogue, the window's drafts, and `MarfaLibrary.linksRevision`, which moves when an edge comes, goes or changes, and when the library is indexed again. Never read `contentRevision` or a whole list while building it, or an edit anywhere rebuilds the open page's header. The relationships are read once for each build. The pictures of the pins' symbols and the types' icons are drawn once for each text size and kept (`PageHeaderIcons`), so only an icon not yet drawn is drawn when a page, a window or a type needs it.
- A title is editable only where the library can set it (`ItemLibrary.canSetTitle(of:)`). An item titled by its first line takes its title from its text, so it cannot be retitled.
- Each window's editor holds that window's title drafts (`EditorController.titleDrafts`, a `DetailsPresentation` keyed by item), so an unsaved or refused title survives switching notes. A refused title is kept until it is saved or discarded.
- `EditorController.flushAll` tries every unsaved title again before it captures the pages. Where a window or the library goes (quitting, changing library, closing a window through `EditorCloseDelegate`), a title still refused stops it as a failed capture does, and the window holding it comes forward and names the item. Deleting items calls `flushAll(leaving: false)`, which saves titles too but never waits on a refused one.
- When a window goes, it calls its editor's `windowWent()`, which drops the window's drafts and removes the editor from `EditorController.open`, so neither takes part in later flushes while SwiftUI still holds the editor for a moment. Closures the editor keeps (header events, observation tracking) and the Format menu's focused editor hold it weakly. A strong capture keeps a closed window's editor, web view, and drafts alive, and `flushAll` would still visit them.
- A right-click on a row of the property block, or on the Linked From heading, arrives as `propertyMenu` (the row's identifier and its frame), and `ItemPageHeader` answers with Hide from Page, which writes the type's `PagePlacements` choice; the page is read again when the choice changes. A row is hidden by not being sent.
- A pin's menu opens under the pin's frame, which the page sends in its own coordinates. `EditorController` converts it to container coordinates, allowing for the covered top and the scroll offset.

## Linking to notes

- A link names a note by a spelling the library resolves to that note alone, from the note it is written in (`ItemLibrary.bodyLink(to:in:)`). In a Marfa library that is the title, unless another note goes by it, the title is shaped like an identity, or the note being written in already links that name to another note (`Item.establishedLinks`, read from the package's own `links(in:)` result, since Marfa keeps the first target of a spelling within a note); then the item's identity names it, with the title as the label (`[[identity|Title]]`). Where no spelling names the note alone, there is no link and the person is told. A spelling a link cannot hold (`[`, `]`, `|`, `#`, `\`, a line break, edge whitespace) is not used (`NoteLinks.canSpell`), nor is a title shaped like an identity (`NoteLinks.canName`), because a link reads that as the item with the identity, not as a title. A file is not a note. A link typed in double brackets becomes a link and is saved as typed, so the page cannot check its spelling; the library resolves it when the note is saved.
- `NoteRequests` is the `notes` message handler. Suggestions come from `NoteLinks.Index`, which runs off the main actor on a copy of the items and keeps titles folded, so typing never waits on a large library. It offers only a title no other note goes by, that is not shaped like an identity, and that the note being typed in has not already bound to another note, since Inkkit writes the name it is given and cannot say which note. It scores with `PaletteMatch`, as the command palette and Link to Note do, from titles it folded once.
- Link to Note asks the person in `NoteLinkPicker`, a sheet of `NotePage` so every window that shows a note has it. The page's request waits on `EditorController.chooseNoteToLink`. The sheet hands back the note's identity, and `finishLinkRequest(choosing:)` reads the link from the library as the note is when it is chosen, so a rename or a new twin since the list was made is seen. Every other end answers the page with nothing, exactly once: Cancel or Escape (the sheet's `onDismiss`), a document replacing the one the command was typed in (`show`), leaving the note, the window going, and the page's process ending. A request made after the window went is answered with nothing.
- Following a link: a command-click on a rendered `[[link]]` reaches `EditorController.openNote(_:from:)`, which asks the library what that very link means (`ItemLibrary.resolveLink(_:in:)`, given its authored raw text and decoded name, heading and alias) and never guesses by title. Only `resolved` opens a note, through `onOpenNote`, which the window carries out as choosing the note in the list does (`Browser.open(linked:in:order:)`: the window's place, search and undo are left alone unless the note is not in the list, which then shows the place that lists it (All Items, or Recently Deleted for a deleted note), and the keyboard stays with the page). Every other answer (missing, more than one note, not looked up yet, refused) opens nothing and beeps (`onUnopenableLink`); no note is made for a link. The heading is scrolled to once the note is on the page (`pendingHeading`), and only if the note has it. A click in a note the page has since left, or in a window that went, is ignored. A window of its own (`NoteWindow`) shows the linked note by handing over its item, as `MainView` does by selecting it; wire `onOpenNote` wherever an editor is made, and ask for the keyboard for the note it opens (`EditorController.focus`), as a main window does with `focusRequest`. An item made in quick add asks for its title (`focus(_:onTitle:)`, which calls the page's `focusTitle`), or, where text was typed, for the text with the caret where it was (`focus(_:caret:)`, which calls the page's `focusText`); the page gives either once it shows that item.
- The page forwards `WikiLinkReference.raw` through `resolve`, `openNote` and its cache key. `NoteLink.raw` retains the authored text inside the brackets, trimmed only as Marfa trims it, and defines equality and hashing. Decoded name, heading and alias serve navigation, never binding identity. This keeps `[[Plan]]`, `[[Plan|Plan]]` and escaped separators distinct even when their display text matches.
- The library reads the exact authored spelling from what the copy bound it to (`Item.boundLinks`, the package's own `links(in:)` result): two links to one name can name two notes, and a renamed note stays the target of the link bound to it. An identity names the item that holds it whatever else is titled. A link the copy has not bound, as one just typed, is `pending`, never guessed from the titles the library holds, since the server may hold another note with that title; it opens once the copy binds it, and the page shows it as an ordinary link, not a missing one.
- The page draws a link whose name no note answers to (`resolve` answered `missing` only) differently. The `resolve` request is answered at once from the library, and `EditorController.watchLinks` tells the page when the library's notes change, once they pause. Never rewrite a note to mark a link.

## Printing and PDF export

- `PrintDocumentRenderer` renders Inkkit's frozen portable HTML in a separate WebKit view, with images supplied through the checked file path above and readable descriptions for other files.
- PDF export renders the complete document, stops at 200 pages or 64 MB, and writes the destination atomically only after rendering succeeds, so a failed export leaves an existing file unchanged.

## Code Review Rules

- **Embed escapes its directory.** Flag any path that reads, serves, or opens an embedded file without `openEmbeddedFile(_:in:)`, follows a symbolic link, or reopens by path. Safe path: use the descriptor `OpenFile` returns.
- **Runnable file opened.** Flag any route that hands a file to another app without `EmbeddedFiles.opens`.
- **Editor made for every view value.** Flag an `EditorController`, a web view, or another costly object made in a view's initializer or given to `State(initialValue:)`. Safe path: `EditorSlot`, or make it in `.task` as Apple's `State` documentation shows.
- **Unguarded private API.** Flag a private WebKit setting set without a `responds(to:)` check, or a new one that Apple's own `WebView` does not use.
- **Link request left open.** Flag a path that ends Link to Note without answering the page once, or that writes a link without `bodyLink(to:)`.
- **Edit saved to the wrong place.** Flag a save without the version it was typed on, or one that can land in another note after the page changed notes.
