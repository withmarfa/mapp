# The Marfa's half of Settings

Status: Overview, Account, Apps, Keys, Addresses, Plugins, Types, Links, Sources, Recently Deleted, History, File Storage, Connectors, Webhooks, Folders, Backups, Updates, Housekeeping, Activity, Monitoring, Limits and Start-Up are built. Folders only reads.

Where it lives: `MarfaSettingsPage`, `MarfaSettingsHost`, `OwnerCalls`, `ClientOwnerCalls`, `AccountModel`, `AppsModel`, `KeysModel`, `AddressesModel`, `PluginsModel`, `OverviewModel`, `ServerHealthModel`, `BackupsModel`, `UpdatesModel`, `HousekeepingModel`, `WebhooksModel`, `ConnectorsModel`, `AddConnectorModel`, `ConnectorMappingModel`, `FoldersModel`, `SourcesModel`, `SourceLimitModel`, `FileStorageModel`, `InstanceSettingsModel`, `OwnerDrafts`, `OwnerPermissions`, `OwnIdentity`, `OverviewPage`, `AttentionConcern`, `AccountPage`, `AppsPage`, `OpenLinksModel`, `OpenLinksSection`, `LinkApp`, `KeysPage`, `AddressesPage`, `PluginsPage`, `PluginCalls`, `ClientPluginCalls`, `PluginWording`, `TypesModel`, `TypesPage`, `LinksModel`, `LinksPage`, `TypeCalls`, `ServerTypeCalls`, `SourcesPage`, `RecentlyDeletedPage`, `HistoryPage`, `FileStoragePage`, `ConnectorsPage`, `ConnectorMappingPage`, `ConnectorHealth`, `ConnectorWording`, `MappingWording`, `WebSignInSheet`, `WebhooksPage`, `FoldersPage`, `BackupsPage`, `UpdatesPage`, `HousekeepingPage`, `InstanceCalls`, `ClientInstanceCalls`, `StoredSettings`, `ActivityModel`, `ActivityPage`, `MonitoringModel`, `MonitoringPage`, `LimitsModel`, `LimitsPage` and `StartUpPage` under `MarfaMac/Settings/Marfa/`.

The Marfa's pages show and change what the server holds for the owner. They use shared Settings components and the host protocol ([Agreed designs](agreed-designs.md#settings), `MarfaMac/Settings/Marfa/AGENTS.md`). Server calls run immediately. Pages show server content only when the sign-in holds the required permission. Otherwise, Needs a Permission explains what the app can't do (`MarfaSettingsPage.permissionLine`). If the server returns `403 forbidden`, the app refreshes the grants and offers Allow More… in the problem row (`OwnerProblemRow`). When the missing permission is the one the page requires, the row uses the page's own explanation.

## What each page does

| Page | Permission to open | What it holds |
| --- | --- | --- |
| Overview | `instance.read` | The Marfa's head card, what needs attention, its name and release, and how it stands. A part the sign-in may not read is left out. |
| Account | none | The owner's username and email as the server holds them (read only), Change Password…, the passkeys (Rename, Remove, Add a Passkey…, which opens the server's own page) and the browsers signed in (Sign Out). |
| Apps | `grants.manage` | Open Marfa Links In, in a section of its own at the top (On This Mac), which needs no permission and shows in every state of the page. Then the connected apps. An app's page holds its access by type, which can only be narrowed, one row for its owner permissions (the same part as a key's), the keys it made, the data it keeps with Remove… (item counts by state, never a size) and Disconnect, whose alert has Also remove its data, off by default. |
| Keys | `keys.manage` | The owner's keys and the keys apps made. A key's page holds its expiry with Extend… (which gives the same key a later end, or none), its tier, its source (set once, shown with a lock), its access by type (narrowing only), one row for its owner permissions and Revoke. New Key… needs `keys.mint`. |
| Addresses | `config.manage` | The sign-in address, the other addresses and the websites allowed to call the server. |
| Plugins | `schema.write` | Installed (named for where the release is read from, withmarfa/plugins or the address a Debug build was pointed at; each plugin with its version, opening a page with what it adds, its Connector row opening the connector's page, its fingerprint and Remove…), Plugin Updates (a newer version the release lists, with what it adds), Available (what the release lists that is not installed, each opening a page of what Install registers) and Install From a File…. A plugin whose types carry guidance installs and updates like any other. Needs `connectors.manage` as well to install or remove one with a connector. |
| Types | `schema.write` | The types the server lists, in Yours (types the owner made), From Plugins (each with its plugin) and Built In, each with its items and what it is based on, and New Type…. A type opens a page of its own. The owner's type holds its name, plural, icon, base (Based On), description (200), guidance and statuses by group: the words a parent gives are locked, the type's own are chips with a plus that adds a word in place, and a word's meaning (120) is in its menu. Its Fields are the ones a type above gives (one locked row, with where they come from) and its own, each opening a page of its own, with Add a Field…; its Feed row sets how many days feed items stay before they go to Recently Deleted (as the type above, never, or 7, 30, 90 or 365 days); its History row sets which edit wins when two meet; and Delete Type… asks first and says in words why the server refused. A field's page holds What It Means (300), its kind (set when it is added), Required, Searchable, Longest (a text field), choices (a choice field), Rename… and Remove…. A plugin's or Marfa's type is not editable: it offers New Child Type… and its icon, and says where it comes from. Guidance is a text area on the owner's types (several lines of Markdown, 1,000 characters counted in code points), kept when the field is left, and shown read only on a plugin's or Marfa's type; the guidance of the types above it is shown on every type. |
| Links | `schema.write`, as Types: it opens from Types' Links Between Items row, which names the first link types and how many there are | The link types the server lists, in Yours (the owner's), From Plugins (each with its plugin, read only) and Built In (read only). Each of the owner's and the plugins' says what it joins and how many each end holds ("From Job to Person. Many to one."). New Link Type… is a sheet: Name, Name at the Other End, From and To (Any Type or one type) and How Many. One of the owner's opens a page of its own with what it joins and Delete Link Type…, which asks first and says in words why the server refused. |
| Sources | `keys.manage` | The sources that hold items, each with its name and mark, which can be renamed or given another mark for every app, and Limit Sources, which needs `config.manage` as well. |
| Recently Deleted | `items.purge` | What the server holds in its bin, Restore on each row and Empty, and how long items wait (needs `config.manage` as well). Show All opens every deleted item as a table page: a checkbox column, the count of those selected in the foot, and Permanently Delete… and Restore for the selection. |
| History | `config.manage` | How long and how many versions of an item the server keeps, and how long it keeps its logs. |
| File Storage | `config.manage` | Where files are kept, how many copies, the free space kept, reading text in files, fetching files from the web and removing files nothing uses. |
| Connectors | `connectors.manage` | Each installed plugin's connector with how it stands and which machine runs it, and Add a Connector… for one that no machine runs. A connector's page holds Run Now, Status, Pause, Runs On, Sign In… (only for a connector whose plugin declares a vendor sign-in), its Settings (a secret shown only as Set or Not Set), What It Brings (each kind opens its mapping page) and Plugin (Show Plugin opens the plugin's page). |
| Webhooks | `webhooks.manage` | Every webhook the server lists for this sign-in, grouped by who made it: the app's own first, then each app and key by name, a key that expired or is gone and an app no longer connected last. A webhook the app made has a page with its address, what it is for (a type or every type), Sending, the events it sends (All Events and one each), its deliveries with Redeliver on every row, and Delete. Another maker's page shows the same read only, with its deliveries and Delete. New Webhook… is a sheet. |
| Folders | none: a folder is read as an item, under the access the app holds to every type | The synced folders the server lists, each with the copies that keep it (named by the sign-in that reports them), how each stands and what needs attention. |
| Backups | `backups.manage` | Where the server keeps its backups (a folder on the machine it runs on) and how often it takes one, which need `config.manage` as well, Last Backup with Back Up Now, and the backups with Restore… on every row. Show All opens every backup as a page, where one can be chosen and restored. A restore asks first, needs a recent sign-in and adds what the backup holds without changing items already here. |
| Updates | `instance.read` | The release the server runs, the steps while it updates, Check Automatically (needs `config.manage`), and how the last update ended. When a newer release is ready, Check for Updates appears beside Update… (needs `instance.maintain`). If the server requires a manual update, Copy Steps appears beside Check for Updates. |
| Housekeeping | `instance.read` | The jobs the server runs by itself with how often, when each last ran and how it went, and the clock hold with Confirm Date… (needs `instance.maintain`). |
| Activity | `audit.read` | The audit log as a table that is a page of its own, newest first, a page at a time, with a filter by kind (Access, Items, Settings, Housekeeping) and a search. |
| Monitoring | `config.manage` | The heartbeat, the error reports and the telemetry the server sends: a switch each, and the addresses and tokens they use, which a row says only as Set. or Not set. under its title, with one button (Set… or Change…). A set one is removed from the sheet that button opens, by Remove… at its leading edge, which asks first. The footer says faults show on Overview too and secrets are never shown. |
| Limits | `config.manage` | The limits the server lets the owner change, each a number followed by its unit: request sizes, rate limits, file reading, connector deliveries, live-update viewers and fetching files. |
| Start-Up | `instance.read` | What the server started with, read only: each setting's name, what it does and whether it is set, never its value. |

## Rules

- **macOS stores the default app for Marfa links.** Open Marfa Links In (Apps) lists apps registered for `marfa://` with their icons and selects the current default. Apps that share a name are labeled with their version and folder when available. The list refreshes when the section appears and when Marfa for Mac becomes active. macOS may ask for confirmation. When the request completes, the pop-up reads the current default from macOS and shows a message if the change failed. If no app is registered, the row shows None. Reset This App’s Settings leaves the macOS default in place.
- **Full Access grants all 14 owner permissions an app can hold.** The app requests all 14 at sign-in, including when you choose Allow More…. Limited grants `instance.read`, `blobs.manage`, and `audit.read`. After approval, the app uses the permissions you chose and tells you if the new sign-in has lost a permission. A page shows Needs a Permission when the sign-in lacks the permission that opens it. Choose Allow More… to request access again.
- **A password is never kept.** It lives in the sheet's fields until the call ends, is never logged, and is cleared on success, on Cancel and when the sheet closes. A wrong current password keeps both fields with the red ring and one line.
- **Narrowing asks first, and only narrows.** An app's access is sent with the access it was read as; a change made elsewhere is told as a conflict, the page reads again and nothing is changed. A key's access is sent with `narrow_only`, and narrowing a key or removing one of its permissions names the change and says it can't be undone. Narrowing a grant that holds only a write to Read Only sends a read in its place, never nothing. Disconnecting an app deletes its webhooks and leaves the keys it made working (`keys-and-oauth/grant-revoke-keeps-keys`, `events/webhook-grant-revoked`). Signing a browser out asks first, naming the browser.
- **An app's data is counted, deleted permanently and never half-told.** Each `app.<vendor>` namespace the app's grant names is read with `GET /app-vendors/{vendor}/data` (`grants.manage`): items by state, no byte size, since Marfa answers counts. Remove… asks first, says it permanently deletes the data, including items in the trash, and that only a backup brings it back, then repeats the call as the package does until none is left. A removal that stops with items left says how many were removed and that some may be left, with why it stopped, and shows the counts read again (or, where that read fails, says the app couldn't read what is left); once any item has gone it never says nothing was changed, and never "done". Disconnect's checkbox sends `remove_data` in the write that disconnects; above 1,000 items the server refuses that, so the data is removed first and the app is disconnected only once none is left. If the disconnect then fails, the page reads the data again and says it was removed and the app is still connected, not that nothing changed. The app's own namespace (`app.marfa-mac`, which holds `app.marfa-mac.preferences`) is shown and never removed or offered in the checkbox here: removing it is Connection's Remove… (and its Disconnect checkbox), which stops `PreferencesSync` first, where a purge from this page would delete the item under it.
- **Only something read before it changed is "changed somewhere else".** That is a grant, a stored setting, or another Marfa now answering at the address (`instance_changed`). A `409` that the server words itself (the sign-in address refusals, a new key's source held by another key) shows the server's words, the source's on the Source field.
- **A key is shown once.** The sheet that follows New Key holds the plaintext; closing it drops it. Copy marks the clipboard concealed and clears it after a minute if nothing else was copied.
- **An address is checked before it is written.** The server's `POST /config/address-check` says what adding, removing or moving would do, and an answer holds only for the address typed when it was asked: typing again drops it until the new address is checked. Moving the sign-in address shows the consequences in the sheet and writes exactly what was checked; the server asks for a recent sign-in, which the package shows in place. Every write names the instance that was read.
- **A draft is handed back when Settings closes or the app quits.** The address typed in Addresses and New Key's name and source go through `Notices.notKept`, as This Marfa's draft does (`OwnerDrafts`). A password is never kept, and a key's secret is never handed over: if the window closes while a new key is shown, the app says the key was made and its secret can't be shown again, so it can be revoked on the Keys page if it wasn't copied.
- **Owner permissions are counted, never all or nothing.** A key's page and an app's page each show one row (`OwnerPermissionsRow`), Look After This Marfa, with "None" or "3 of 14". With some held it opens a page of its own (pushed, Back returns) with one switch each; a switch can only be turned off, and turning it off asks first. New Key shows the same row with Choose…, which turns the sheet to a page of switches and back.
- **A sheet is shown by the window.** A page hands its sheet to `SettingsSheetPresenter` (`settingsSheet(presenting:)`), which draws it in the middle of the whole window, not under the toolbar; what it shows is read from the page's model. A sheet grows with what it holds up to the window's height, then its content scrolls between its title and its buttons. A field's placeholder says something its label does not (the address field's "https://"), never the label again.
- **The server's own settings are sent at once, one page at a time.** History, File Storage, Recently Deleted's wait and the Overview's name are `InstanceSettingsModel` settings, sent by `PATCH /config` with only the setting changed and the instance read. A pop-up or switch sends when it changes; a number or the name sends on Return or when the field is left. A page saves only the settings it shows, so what another page holds typed is not sent by it. A setting the server does not hold shows the value the server documents as its default in the pop-up ("30 Days"); the menu's item for the default reads "Default (30 Days)" and removes the setting.
- **Keeping things for less time asks first.** A retention that is shorter than the one the server holds (or may be, where the server holds none the app can read) asks, names what it removes and says it can't be recovered. Keeping things as they were puts the pop-up back. Zero days is no limit where the contract says so (deleted items, activity, events, table changes and connector deliveries) and an empty window for versions. Keep Free on Disk asks the same way when it is lowered, naming the new and old values, since a number typed on the way to a larger one is sent when the field is left. A question still open is dropped by Revert and by closing Settings, a second save waits until it is answered, and a change already agreed to is not reported as left unsaved when Settings closes.
- **One reader of the server's health.** `Server.health()` in the package (`GET /health`: the open fields for any sign-in, the detail for one holding `instance.read`) is read once by `ServerHealthModel`, which the host holds, and Overview, Backups and Housekeeping all read it. A part is Working, Needs Attention or Not Working from its own status (Database is the worse of its read and its write), never from a concern's title. Where health could not be read, Database, Disk, Files and Backups say Couldn’t Check, never Working. The server's own `error` and `lastError` texts are never shown: each page words a title and one plain line from what the server counts (`UpkeepWording`).
- **Overview reads what the package offers.** Needs Attention is `GET /attention`. Each concern shows the server's title and one plain line the app words from its kind and reference (`AttentionConcern.shownLine`), never the server's own message, which names settings by key and requests by path; where the app has no wording, the title alone. A concern the app cannot place stays under Needs Attention. A development build reports version 0.0.0, which is no version, so its Marfa row is left out and only an update line shows. The Database and Files sizes come from `GET /metrics`. If the size read fails, the health rows still report their status and the size failure gets its own row. If the update status read fails, Overview shows the failure and uses the installed version from metrics when available. The server does not give free disk space, so Disk says Working or what the server says is wrong. Backups is a link to the Backups page where the sign-in may manage backups, and a ready release links to Updates, which carries a badge of one.
- **Needs Attention shows only the action that exists.** A concern opens the page that looks after it where the sign-in may open that page: a key concern Show Keys, a backup concern Show Backups, a job or clock concern Show Housekeeping, a folder concern Show Folders and a secret Monitoring holds Show Monitoring. The others (health, connector, fault and unavailable) say what is wrong and offer nothing until their pages exist. A setting the app has no name for is titled "Set a Secret Again", never by its key. The app's own row, "This App Can Look After Part of <Marfa>", with Allow More…, comes first while the sign-in lacks anything a sign-in asks for (`MarfaSettingsHost.lacksAsked`): an owner permission, or a scope the app began to ask for after the sign-in was made. The sidebar's badge counts the server's concerns only.
- **Sources are written to the server for every app.** A rename or mark needs the server and is never queued; a refusal keeps what was typed in the sheet. Limit Sources is the server's source filter (`enforcement.source_filter`): written whole with the other two levers as they were read, so a change made elsewhere before the write is told and not written over; the contract gives a config write no version, so a change in the moment between the read and the write is not caught. Another Marfa answering at the address is told in the settings page's words, and the draft starts again from it. Types are checked, then sources; a limit that names types and no source waits, since it would hide every item of those types from every app. Turning the limit off asks for confirmation before it clears the filter.
- **Stored settings are written after a fresh read.** Monitoring and Limits send a change only once a read of `GET /config/settings` finds each setting it changes as the page showed it, and name the instance that was read; a setting changed elsewhere is told in a notice that names it ("Changed Elsewhere": "<Setting> was changed elsewhere. The app read the new value; yours wasn't saved."), the page shows what is there now and nothing is written over it, and the notice closes when the person next edits or chooses Close. A write the server answers as a conflict is told the same way. Another Marfa answering at the address is told as that, in one line under the setting (the sentence Overview uses), and nothing of it is adopted: the page keeps what it showed and sends no retry to it. A write that arrives while another runs waits for it. If the read after a successful write fails, the page keeps the values it sent, so a later write is not told it changed elsewhere.
- **A limit is checked before it is sent.** Each limit has the contract's range, in what the server holds; sizes are shown in megabytes (1 MB is 1,048,576 bytes) with thousands separated, and numbers are grouped, pointed and parsed as the Mac's region writes them (a separator the region does not use is refused, never guessed at). A value out of range, or not a number, stays in its field with the red ring and one line, and nothing is sent. A field emptied removes the stored value, so the server's default applies. A value is sent when the field is left or Return is pressed.
- **A secret’s row shows “Set.” or “Not set.”** The server never returns a secret. To change it, type the new value in the secure field. Closing the sheet discards the value without handing it over. The sheet uses a plain field for a setting the server lists as non-secret. Select **Remove…** at the leading edge of the sheet. The confirmation explains what stops. Set the PostHog host and project token together when configuring error reporting. Removing either also removes the other. You can turn on the heartbeat or error reports once a receiver is set.
- **The audit log is paged by cursor.** The server gives no count and no way back, so the page says which entries it shows ("1 to 20") and keeps where each page began for Newer; Newer and Older appear only where there is another page, and a read that fails for a new filter shows no rows of the old one. They are text buttons because text says more than chevrons. An action is put into the app's words; one the contract does not name is put into words from its own name.
- **The plugins release is read by the app itself, not through the server.** `PluginRelease` (the package) reads `plugins.json` and each bundle from the latest release of the plugins repository, sending no credential, and a bundle is used only when its SHA-256 is the one the index lists, as the command line does. This is a connection the app makes of its own, to GitHub, apart from the Marfa server. The page shows Installed as soon as the server answers and reads the release after, under Available ("Reading the Plugins Release…", then Try Again if it cannot be read, which drops every bundle read before); Remove and Install From a File… work throughout. A bundle whose digest is not the listed one is never shown or sent, and neither is one whose version or digest differs from what a fresh index lists (the release changed since it was shown). Try Again reads the release again, then the bundle that read lists, or says that the release no longer lists the plugin. A read that was cancelled puts back the release and the bundles held before it, and is not a failure. A first read that never finished does not stay on "Reading the Plugins Release…": Available offers Try Again. A Debug build reads the release `MARFA_PLUGINS_URL` names, as the command line does, and Installed names that address in place of withmarfa/plugins.
- **A link type is registered and deleted only by the server's answer.** New Link Type… registers the type under `user.`. The ID uses ASCII lowercase letters, digits, and underscores after the prefix and fits the 128-byte limit. Just before sending, the app reads the list again and avoids the IDs and reverse names it holds (`edges/types-name-held`); a list it can't read sends nothing and says why, with Try Again. The sheet's fields are frozen while the server answers. Registration needs `metadata.edge_types:write`, which every sign-in asks for. A sign-in that lacks it is told in the sheet, with Allow More…; an approval clears the refusal only when the new sign-in holds that scope, and otherwise says it is still missing. A refusal keeps what was typed, and Settings closed after one hands back every field. Delete Link Type… sends nothing until the owner agrees in the alert, then reads the list again and sends nothing unless the type under that ID is still the one the alert showed and still the owner's. Each question is answered once: answered again, it sends nothing. It never forces, and a type links still use is kept and told (`edges/types-delete-in-use`). After either answer the list is read again, so it shows what the server holds.
- **A bundle is installed as its bytes.** The server records the SHA-256 of what it receives as the plugin's `fingerprint`, so Install, Update and Install From a File… send the bytes the release served, or the file's, unchanged (`Server.install(pluginBundle:)`), and the fingerprint then equals the release's digest or the file's.
- **A plugin whose types carry guidance is sent like any other, and the server's answer decides.** the app has no rule of its own about guidance. Install, Update and Install From a File… send through the package's confirming `Server` (the one Backups' Restore uses), so a `401 insufficient_user_authentication` shows the browser sign-in in place and sends the bundle once more; the app draws nothing for it. A sheet the owner closes (`MarfaError.canceled`, `PluginFailure.canceled`) changes nothing and says nothing; a decline (`forbidden` `access_denied`) says nothing was installed. While a Marfa still refuses guidance from an app (`plugins/install-guidance-app`, `MarfaError.pluginInstallRefusal` `.carriesGuidance`), the page says so and gives `marfa plugins install <name>` (or the file's path) with Copy in place of Install.
- **Updates add and never remove.** A newer version may only add (`plugin_narrows` refuses the rest), so Plugin Updates says what the version adds, read from its bundle, and that nothing is removed. A server too old for a plugin (`409 plugin_needs_newer_server`) is told with both releases.
- **Removing keeps the types and their items, and deletes the connector's mapping.** Remove… asks first: removed are the connector, its settings and secrets, and its saved mapping with any rewrite it asked for (`plugins/mapping-removed`); kept are the plugin's types, their edge types and the items they hold, counted from the open copy (active items). The server's answer (`removed`, `kept`, including `kept.connector`: the source keeps its state and its agreements) is what the page tells afterwards. The app never refuses a removal itself; a server refusal, such as a missing `connectors.manage`, is shown in words with Allow More….
- **Problem rows use app wording.** Failed reads say what couldn't be read and offer an action when available. The app keeps server error details in its local log. A field can show the server's reason for refusing a change when it holds no setting name, code, or route.
- **A connector's health is derived, in this order.** The server gives no health word, so `ConnectorHealth.of` takes the first that holds, from `GET /plugins/{name}/connector` (`paused`, `host`, `registration`, `run_requested_at`), `GET /connectors/{registration}` (`last_heartbeat_at`, `last_run`, `problems`), the host's `last_seen_at` (`GET /connector-hosts`) and the settings' `missing`: **Paused** (the owner paused it); **Needs setup** (a required setting has no value, named in the page's line); **No machine** (no host); **Waiting to start** (a host, but no registration yet: the line says whether the machine has been seen); **Not heard from** (the latest of the heartbeat, the last run's end and the machine's last visit is over an hour old); **N problems** (the connector reports problems of its own, which the page lists under Needs Attention as it wrote them); **Last run failed**; **Run requested** (Run Now was asked and the connector has not yet reported a run for it); **Ran <time ago>**; **Hasn't run yet**. A connector whose control could not be read, or whose registration it names but could not be read, is "Couldn't read", never "Waiting to start". Green is Ran, orange is any word that needs the owner, grey the rest.
- **Pause, Resume and Run Now are stored choices.** The server keeps them and the connector follows them at its next run, which the page says under Running; the app never starts a run. Run Now is refused while paused (`409 connector_paused`) and the page shows the server's line, which holds only the plugin's name. While a run is asked for, the open page reads the connector again every five seconds, up to ninety seconds. "Run requested" ends when the connector reports the run (`run_requested_at` clears then, not when the connector takes the request), so a run that lasts longer than ninety seconds keeps "Run requested" until the page is read again.
- **A connector's settings come from the server, as it declares them.** A label is shown in title case whatever the plugin wrote; a switch, a pop-up, a text or number field sends when it changes or the field is left, and an empty field takes the value away so the default applies; a refusal keeps what was typed and is handed back when Settings closes. A required setting with no value shows "Needed before it can run." A connector with a vendor sign-in does not show the setting that sign-in sets.
- **A connector's secret is only Set or Not Set.** It is set or changed in a sheet with a secure, one-line field that is never handed over, held in a draft or given to the accessibility tree, and dropped when the sheet closes. The row holds Set… or Change… alone; Remove… at the leading edge of the sheet, for a secret that holds a value, closes the sheet, asks first and sends `null`. A secret the server cannot read (the Marfa was restored or moved) says so and is set again. The field is one line: a setting's `kind` is `text` for every secret, so a bundle cannot say that a secret (GitHub's private key) holds several lines, and the app does not guess from a name. `marfa plugins secret` sets it from standard input.
- **Which machine runs a connector is chosen from the machines Marfa knows** (`PUT /plugins/{name}/connector`). No Machine sends `{"host": null}`; for a connector that is running (on a machine and not paused) it asks first and says the connector stops until a machine is chosen, and the server revokes the key the machine minted for it. Where no machine is known, the row says so and points to Add a Connector….
- **Add a Connector… places a connector that no machine runs** (S72). Its sheet offers those connectors, and Runs offers each machine Marfa knows ("On <name>") and On Another Machine; there is no On This Mac, because the app cannot run a connector. A machine already linked is only assigned, and the sheet closes. On Another Machine asks for the machine's name (1 to 100 characters, as the server takes it), makes the machine with `POST /connector-hosts`, assigns the connector, and shows the Command to Paste There: the plugins release's installer, `curl -fsSL <release>/install-host.sh | sh -s -- '<link>'`, as the plugins repository's host README gives it. A machine never linked gets a fresh link (`POST /connector-hosts/{id}/link`), which ends its old one. If the assignment is refused, the machine just made is removed. The link gives the machine a key, so it is shown once, in a field that truncates its head: it is never logged (its type's description leaves it out), never kept in a draft or handed over, and closing the sheet drops it. Copy Command puts it on the clipboard concealed and takes it off after a minute (`OwnerClipboard`). A link the shell would read as more than one word is never made into a command. When its 15 minutes pass, the sheet drops the link and offers New Link. Settings closing while the command shows tells the owner, in a notice that holds the quit, that the link can't be shown again and how to add the connector again; one still being made is told about when its call ends.
- **A vendor sign-in goes through the Marfa.** Only a connector whose plugin declares `sign_in` shows Sign In…. The app starts it with `return_to` set to its own registered redirect (the server accepts that only from the app that registered it), shows `url` in the system's web authentication sheet (`WebSignInSheet`) and then reads `GET .../sign-in` for `status` and `reason`. A sign-in that cannot start because the client settings are not set (`409 connector_sign_in_settings_missing`) says "Set <labels> first."; a failure is put into the app's words from the one outcome word and never shows the provider's text; a sign-in started by a key, not an app, is refused by the server and says the app needs to be signed in as an app. "Signed In" is the sign-in's token setting holding a value.
- **What It Brings is read from the plugin's bundle** (`connector.kinds`): each kind with the type it is written as and which way it moves, and each row opens that kind's mapping page.
- **A kind's mapping is saved as it is made** (`PUT /plugins/{name}/connector/mapping`, `ConnectorMappingModel`). The page shows the owner's draft beside what the server stores: a pop-up or switch saves at once, a template or fixed value when its field is left or submitted. Each save sends the stored entry of every other kind, so a kind the server refused does not hold the others back, and one save runs at a time. A refusal names a place in the kind's entry. A field's (`kinds.<kind>.fields.<field>`) is shown on that field, in the app's words where the target type needs a field nothing fills, including a template or a fixed value left empty ("Job needs Client. Choose a field or a fixed value."), and in the server's otherwise. A refusal of the target type (`kinds.<kind>.target_type`) is shown on As, every one of them. A status word's (`kinds.<kind>.status_overrides.<word>`) is shown on that word's row. Anything no row on the page shows is shown on a row of its own. Every fault is shown, with "<Marfa> kept the mapping as it was." under the card; the draft stays. A stale save (`409 connector_mapping_stale`) keeps the draft and says so; Reload reads the mapping again and saves the draft onto it. A reading older than the version held, or one that arrives while a save is in flight, is not applied. Changing the target type fills each field both types hold from the kind's own, as the server does, and empties the status overrides. A fixed value or template left empty fills nothing; a number typed is sent as a number, and a word is refused before it is sent. A field of the target type is filled from a field of the kind's own type of the same sort of value, a fixed value, or (for text) a template, which the page marks as not written back. Status words map by group, with an override per word of the kind's own type (`status_overrides`) once a status field is filled from a status field.
- **A preview is asked for the draft and waits for the connector.** `POST .../connector/previews` with the draft (or none where nothing is unsaved), then `GET .../previews/{id}` every two seconds until it is ready or failed. The connector answers at its next run, which the page says. A preview the server stops keeping, or whose time passes, is shown as expired with Try Again, and one that cannot be read is shown as unavailable with Try Again. A poll from an older ask, including one that fails, does not replace a newer preview. A paused connector, or one on no machine, answers none, and the page says so without asking. A new change replaces the one being waited on.
- **Existing items change only when the owner asks.** The page counts them with a dry run (`POST .../mapping/rewrite`, `dry_run` true). Changing the target type clears that count, and a dry run that fails clears it and says so, with Try Again, so Apply to Them… is offered only when the draft is saved and the count just read for that mapping is above zero. The question names the count. The request is shown as pending from `rewrites` until the connector clears it. A re-read that fails after Apply is shown: the request was made, and the app could not read it back to show it, with Try Again.
- **A webhook's signing secret is shown once.** The sheet that follows New Webhook holds it, and closing the sheet drops it. Copy marks the clipboard concealed and clears it after a minute if nothing else was copied (`OwnerClipboard`, which a key's secret uses too). If the window closes while it shows, the app says which webhook was made and that its secret can't be shown again, so the webhook can be deleted and made again. The page reads back only the last four characters.
- **A page shows its list before the rest is read.** Webhooks and Folders show the list as soon as it is read, then fill in each webhook's Sending and each folder's standing, four reads at a time. Webhooks also fills in type names after showing the list. After a webhook is made, the list refreshes independently of those reads.
- **A key's expiry is extended, never changed in place.** Extend… (`KeysModel.beginExtend`) is on a key that ends, offered only with `keys.manage`; without it the row says what the app isn't allowed to do, with Allow More…. The sheet offers the days later than the key ends now (7, 30, 90 and 365 from today) and Never, and sends only `expires_at` (a date, or `null`) with no `narrow_only`, which the server refuses a later expiry under (`keys-and-oauth/expiry-manage-lengthens`); the key's secret stays, so the sheet says nothing using it changes. Where the app is signed in with a key that expires (a test key; a signed-in app counts as having no expiry), the choices stop at that key's own end and Never is not offered (`keys-and-oauth/expiry-manage-ceiling`); the app reads that from `GET /keys/current` (`OwnerCalls.identity`), which a signed-in app's token answers with `403`. Until that is read nothing is offered, and the expiry row shows the failure with Try Again (`KeysModel.identityFailure`), since an end not known is not no limit. A refusal keeps the sheet and the choice, with the red ring on the pop-up and one line, and has the grants read again. A key that never ends has no Extend…. Making a key end sooner is not offered: Revoke ends it.
- **A sign-in that holds `webhooks.manage` and `keys.manage` sees every maker's webhooks.** The list is the server's (`events/webhook-owner-list`), grouped by maker (`WebhooksModel.groups`); a key's maker is told as the key, an expired one by reading the keys, and a maker the server has no name for as a revoked key or an app no longer connected. Which are the app's own is matched by identity with who the app is signed in as (`OwnIdentity`), never by name: the key's id for a key sign-in. A signed-in app has nothing to match, since a webhook's maker is its OAuth client ID, which neither the server nor the package tells an app about itself, so none of an app's makers is taken as the app's own: all stay read only and Delete…, and New Webhook… makes under an empty own group. If the identity can't be read the page shows the failure with Try Again, and when the permissions change what the list holds (Manage Keys lost or gained) the list is dropped and read again (`WebhooksModel.readAgainIfScopeChanged`). Only the app's own can be changed or sent again; another maker's page shows no Change, For, Sending, event switches or Redeliver, and Delete… asks first, naming the maker (`events/webhook-owner-delete`, `events/webhook-owner-no-change`). Without `keys.manage` the list is the app's own, with a row that says the others need Manage Keys and offers Allow More…. Turning Sending off asks first and names what it drops (the deliveries waiting). A change to the address, the events or the type is sent alone, with no version: the server changes each in place, and a webhook found gone is told as gone. A change to the events is built on the webhook read again just before it is sent, so an event another app turned on or off since the page was read is kept. That narrows the window and does not close it: with no version to send, a change made between the read and the send can still be replaced (withmarfa/marfa#3408 asks for one). Redeliver is shown on every delivery and enabled only on a failed one of a webhook that is on (`events/redeliver-inactive`); a refusal from the server, such as a delivery older than the audit retention, is shown as a line under the table.
- **A folder is read, not changed, here.** The package's client holds only the folder status call; reading and changing a folder's settings and files, and listing its paths, are the working copy's, which keeps no `system.*` rows and which the app does not use for folders. The list comes from the server's overview (at most 30 folders, by title; where it cut the list, the page says "Showing 30 of N" and that `marfa folders inventory` lists the rest) and each folder's copies from its status report. The report holds counts and problem codes and no file names. Removals that wait are decided on the machine that holds the copy, so the page says where to look and offers no action.

- **Backups keep to what the server offers.** Where backups go is a folder on the machine the server runs on, typed as an absolute path in a sheet (the app cannot browse that machine), changed with `PATCH /config` after a recent sign-in, which the call shows in place; an object store the server was set up with is shown and never changed here, and the server allows only one of the two. A restore is `POST /backups/{instance}/{name}/restore`: it asks first and lists what a restore leaves out, needs a recent sign-in, and keeps the sheet open if that is cancelled. After it, the page says how many items were added and how many were already here, and names any secret to set again by the name Monitoring gives it ("The heartbeat address and the PostHog project token."); a setting the app has no name for is only counted ("2 other settings are set on the machine <Marfa> runs on."), never told by its key. A refused folder change stays in its sheet, and only the interval and Keep Backups In pop-ups leave a line on the page, cleared when the sheet opens or closes. A server value with no time of day shows no time. Where the sign-in may not read the server's backup detail, the destination says Couldn’t Check, and a status with no count is worded as the server reported it ("Backups are failing", "Backups are incomplete"). Back Up Now with nowhere to keep a backup sends nothing and says so.
- **A problem row's title is a sentence.** Every title in Needs Attention on Backups, Updates and Housekeeping reads as a sentence in sentence case ("No backups are kept", "The update to 0.0.85 didn’t work", "Clean-up is paused"), as the boards draw it.
- **An update is followed to its end.** Update and Try Again ask for confirmation before starting `POST /update` (Check for Updates runs the server's `release-check` job, then reads again) and the page then reads the update every two seconds. The server ends itself to start the new release, so a read that fails meanwhile is Restarting, not a fault; after 90 reads that go unanswered the app says it stopped waiting, and offers Check Again rather than Update, since the server may still be updating; any read of the status clears that. One follower reads at a time and ends with the page. The page follows an update already in progress before reading the automatic update setting. When the Change Settings permission changes, the page reloads the setting. The server answers a second start with the update that runs, in the same 202, so a start is followed whichever it was. Check for Updates is off while Check Automatically is off (the server runs no `release-check` job then and answers 404), and the row's line says why. Without `instance.maintain` the Check for Updates and Update buttons are one Allow More…. An update the server put back, or could not finish, is told in Needs Attention in the app's words with Try Again and no second Update. Where the server cannot update itself the page shows the server's own step, which is an instruction to copy, with Copy Steps.
- **Housekeeping lists the jobs an owner knows**: Back Up, Empty Recently Deleted, Thin Old Versions, Remove Old Activity, Remove Unused Files, Copy Files to Storage, Read New Files and Check for Updates, with the server's intervals and no Run Now. Its other jobs tidy the server's inside and are not listed. Confirm Date… reads health again and asks with the date the server's clock reads then, always with its year. `POST /clock/confirm` takes no date: the server trusts its clock as it reads at that moment, and answers it as `confirmed_at`; where that is not the day shown, the page says so under Needs Attention.

- **A type is changed as the server holds it.** `PUT /types/{id}` replaces the whole definition and has no version, so a change reads `GET /types` again, makes the one change (`TypeDefinitionEdit`, which the field edits use too) and sends the type back, with its guidance as it was unless the change is to the guidance itself: a replacement that left it out would remove it. The server's `400 invalid_schema` names a field in `details.errors`, which the page shows on the field it names with what was typed kept; a status word is made from what is typed (lowercase, an underscore for a space), and the server judges it. Lengths are counted in Unicode code points, as the server counts them. Changes to a type, and its icon, run one at a time, in the order they were made, so each is built from what the one before it left. Each is judged against the type as the server holds it when it is sent, never against what the page showed when the person acted: a change the type already holds sends nothing, a choice is added or taken out by its word and never as a whole list, and a change back to an earlier value is still sent behind the one in flight. What was typed and not kept while a change is queued is handed over when the queue ends. A field is named from its label when added and keeps its name when renamed, since items hold their values under it; removing a field leaves each item's value (`types/field-removed`). A type is deleted only while no item, in the bin too, holds it and no type is based on it (`types/delete-in-use`, `types/delete-subtypes`), and never forced. A type's provenance comes from `GET /types` (`provenance.origin`), since the catalogue holds none; a plugin's type is told apart before sending only by what the list says, and `common` stays reserved. **Guidance is saved like any other change, and the server's answer decides.** It goes through the same queue (`TypeEdit.guidance`) and the same confirming `Server`, so a `401 insufficient_user_authentication` shows the browser sign-in and sends again. The text is kept when the field is left and is trimmed at both ends, so a field opened and left again sends nothing, and over 1,000 code points is not sent. While a Marfa refuses guidance from an app (403 with `details.changes` naming `guidance` and no `required_scope`: `types/guidance-app-made`), the typed text stays, and the field says this Marfa takes guidance only from the command line for now, with `marfa types replace <id> --file <id>.json` (the CLI reads `<id>.md` beside the file as the guidance) and Copy. A refusal that names `required_scope` is a missing permission and shows Allow More…. A sheet the owner closes saves nothing and says nothing, and the same text is not sent again until it changes; a decline says the type was not changed. The text area is plain text, so quotes and dashes are never replaced.
- **A new type is made under `user.`**: its identifier is its name in lowercase letters, digits and underscores, made unique among the listed types, and its base is the type it was made from. It declares no field of its own.
- **A status panel's Edit Statuses…** closes the panel and opens the item's type in Settings > Types.

## Left out

- Name and picture, which the app does not ask to change, and Add Passkey's list refresh after the browser returns.
- Overview: Update beside the release (a ready release links to Updates).
- Types: Strict and Keep Versions are not offered among a type's rules, and a field's menu's Edit the type in Settings is not built. A type's Show Items button.
- Links: how many links each type holds and the line for the built-in types nothing uses yet, which need the server to count edges by type (withmarfa/marfa#3533); changing a link type's ends or names, and its properties.
- Sources: the Who May Write rule (`enforcement.source_allowlist`) and a source's own page.
- File Storage: Show… for the files nothing uses (a list of them has no use without their names) and the object store's secrets.
- History: the webhook deliveries are kept as long as activity (`audit_retention_days`), so they have no row of their own.
- Recently Deleted: the colored type mark on each row.
- Apps' Tidying settings and the Private Addresses switch, which need server or settings-model work.
- Webhooks: a webhook's signing secret can't be changed: the server changes it only by making a new webhook.
- Connectors: a new link for a machine that never used its own, other than by No Machine and Add a Connector… again, and removing a machine (`marfa hosts` does both), Files and pictures in a kind's mapping (the contract has no member for them: withmarfa/marfa#3505), a connector's runs, the old board's Source, Key, Edits Put Back and Inbound Addresses rows (RSS's board S76 is an older design, so RSS is the same page as every connector) and a multi-line secret.
- Plugins: where an installed plugin came from beyond the release it matches (the server records the installer, not the place), the edge types by name (the server lists only their IDs), and the health on the connector row (the Connectors page owns it).
- Folders: renaming, the tree of what a folder holds, the ignore and include patterns, the removal and addition limits, Read Every File Every, Stop Syncing and a button for removals that wait. Each needs the server's folder doors (`GET /folders`, `PATCH /folders/{id}` and `POST /folders/{id}/revoke`) or the paths of the `in-folder` edges, none of which the package's client offers. Read Every File Every is the copy's own setting, never the server's.
- Backups: Export Everything and Restore an Archive (files the app reads and writes itself, which On This Mac's export covers for the owner's own items), adopting another instance's backup folder, and choosing an object store.
- Keys: making a key end sooner, and the Needs Attention row on the list for a key that ends soon, which has no rule yet for how soon. The Overview shows the server's own concern for it.
- Housekeeping: Run Now, and the jobs that only tidy the server's inside.
- Activity's total count and a "Who" or "What" that names the item, which the audit log does not give.
- Limits the board does not draw: the file inflation and memory caps, the inbound byte caps and the held and kept delivery counts, and the retention periods, which belong to the pages that own them.
- Telemetry's per-signal addresses and headers, its sample rate, service name and resource attributes.
