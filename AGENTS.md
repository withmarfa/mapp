# MAPP

This file governs every session that works in this repository.

## What this repository is

MAPP: a native macOS markdown notes app with a sidebar, a list and a page, in the manner of Notes and Mail. SwiftUI throughout, AppKit only where SwiftUI cannot express something. Notes are markdown files in a folder the person chooses.

## Conventions

- **American English** in code, comments, commits and repository files.
- **Scoped Conventional Commits**, for example `feat(app):`, `fix(editor):`, `test(model):`. Present tense, lowercase, short.
- **Branches and pull requests.** Work goes on a branch and reaches `main` through a pull request, squash-merged once the tests pass and a reviewer has read it. There is no CI; the tests are run locally before merging. Once the work is merged, bring the local `main` up to date (`git pull --ff-only` on `main`) so the next piece of work starts from it.
- **Comments explain why, not what.** A comment survives only if it carries a reason the code cannot.
- **No personal detail.** No absolute paths, machine names, account names or credentials in any file here.
- **No legacy.** No compatibility shims, deprecation aliases or migration paths. Removed means gone.
- **No time estimates.**

## Platform

- macOS 27 and Xcode 27 only. No `#available` checks and no fallbacks for earlier systems.
- Swift 6 language mode, main-actor isolation by default, Swift Testing.
- Native containers and controls (`NavigationSplitView`, `List`, toolbars, commands, system materials) so the system supplies the look. Custom chrome needs a reason. Check API and design questions against Apple's documentation and the Human Interface Guidelines, not memory.
- **Aesthetic.** The app should feel like the Codex app or Craft Docs: Apple's system components, done nicely and customised with care, not a web app's chrome. The Liquid Glass toolbar buttons, the sidebar and the split view stay the system's; what the app adds (the palette, the column search, the page) is drawn to sit beside them as if it were theirs.
- The toolbar over an item (`MAPP/Views/NoteToolbar.swift`) has one trailing group: New Item (plus), Format (Aa), Details (information circle), and More. Format includes lists and table insertion; More includes Share and Add Attachment, which opens the existing image attachment chooser. Once the page header scrolls away, the item's title appears at the leading edge. The title and New Item stay fixed; the other toolbar items are customizable, and every action is also a menu command, since a toolbar can be hidden or changed. The command palette on ⌘K (`MAPP/Views/CommandPalette.swift`) offers the same commands, the sidebar's places and the notes by title, and lists only what could be done at that moment. Search lives in the list's column, as Mail's does: a button beside Sort becomes a field across the column (`MAPP/Views/ColumnSearch.swift`, the system search field, since SwiftUI's own search goes to the window's end), which ⌥⌘F opens. Its native close-button accessory remains visible even when the field is empty, because closing search also restores the column's toolbar. ⌘P opens the palette searching the text of every note. ⇧⌘P prints, since ⌘P is search.
- App Sandbox and hardened runtime stay on. The sandbox allows outgoing connections only because WebKit's page process needs them; the page itself loads nothing. Every user-facing string goes through the String Catalog.
- A checkout builds without a developer account and signs to run locally. `Config/Signing.xcconfig`, the project's base configuration, leaves the team empty and includes the ignored `Config/Local.xcconfig`, which `aic-infisical-run -- scripts/render-local-signing.sh` writes from Infisical to sign with the team. Never commit a team identifier or edit the rendered file by hand.

## Versions

- A version exists only as a git tag: `v` followed by the version, such as `v0.0.5`. Agents create the tag when a release is called.
- Every version is `0.0.x` until the first public release, because WithMarfa keeps every version inside its code at 0 until then. Each release is the latest tag plus `0.0.1`, so `v0.0.5` follows `v0.0.4`.
- Agents never write a version into a file: `MARKETING_VERSION` stays `0.0.0` in the repository, since `ci_scripts/ci_post_clone.sh` sets it from the tag in the cloud copy only.

## Layout

- `MAPP.xcodeproj` is a native Xcode project whose `MAPP/`, `MAPPTests/` and `MAPPUITests/` groups follow the folders on disk; add files by creating them, not by editing the project file. The bundle identifier and display name live in the target's build settings. `MAPP/Info.plist` holds only what build settings cannot express (the note drag type) and is excluded from the app's resources.
- `MAPP/Model/` holds the notes model, free of SwiftUI; `MAPP/Views/` the windows and panes; `MAPP/AppIcon.icon` is the Icon Composer app icon. `MAPPTests/` holds the Swift Testing unit tests, hosted in the app; `MAPPUITests/` the XCTest UI tests that drive the running app through its accessibility tree. `Design/` holds artwork that is not built into the app.
- `MAPP/Localizable.xcstrings` is kept in sync by building in Xcode; `xcodebuild` alone does not update it.
- `editor/` is the note editor: Milkdown on ProseMirror in TypeScript, built by Vite into one self-contained page, `MAPP/Editor/Page/editor.html`, which is committed so the app builds without Node. After changing anything in `editor/`, run `pnpm build` there and commit the page with the change. `MAPP/Editor/` holds the Swift side: the web view, the controller that drives the page, and the bridge's messages. The page fetches nothing and never navigates: images in the notes folder reach it from the app, and any other image shows its name. An image's width, set by dragging its edge, is kept in its alt text as `![name|400](…)`, as Obsidian reads it. A note's text runs to a reading width, which Settings adjusts, unless Full Width is chosen in the View menu or Settings; the width comes from the page's margins, so a click beside the text still places the caret. Text and reading width use `rem`; the native header's measured height reaches the page in pixels. Printing and Export as PDF print the page itself through WebKit, laid out by its `@media print` styles, which remove the header's reserved space. The native item header overlays the page, whose top padding reserves its measured height. WebKit's scroll offset reaches the native header through the script bridge, so the header scrolls with the body and clips away at the top. `MAPP/Editor/ScrollingHeader.swift` hosts the native controls and forwards their unhandled wheel events to WebKit through the public AppKit responder API, because the sibling views' responder chains do not meet. Opening a note starts at the top without focusing the editor; heading marks and selection outlines appear only while editing. WebKit lets the window background through; the toolbar and find bar have a fixed inset, updated only when layout changes (`MAPP/Editor/WebViewChrome.swift`, `WebViewContainer`). The header is also offset below the find bar.
- Settings (`MAPP/Views/SettingsView.swift`) fills the current main window with a native `HSplitView`: Back, Search Settings and categories in the sidebar, and the selected preferences in the detail. The existing three-column workspace stays mounted underneath, preserving the selection, column widths and unsubmitted draft. It is hidden and disabled while Settings is open, and its focused command values are cleared. Settings opens through the same presentation from the app menu, ⌘, and the command palette; a request from a note window or with no main window opens a main window. Settings search filters categories by their names and preference labels. Returning restores the retained workspace. Changing the notes folder flushes the open editors before choosing the new library.
- `MAPP/Types/` holds Marfa Types, which sits with Recently Deleted at the foot of the sidebar, below however many folders there are (a second list, sized to its rows, so the arrow keys do not cross into it; ⌘K reaches both): `marfa-types.html` is a copy of the page Marfa's type browser generates from its type definitions, self-contained with its own navigation and search, and is refreshed by replacing the file whole, never by editing it. Picked, it keeps the window's three columns: the page's own list of types where the note list goes and the chosen type where the note goes, the same page loaded twice with each showing one part and following the other's fragment. The window never changes its columns, since AppKit crashed laying out the toolbar as the columns changed with the sidebar hidden or resized. The list column's search there searches the page rather than the notes, as do Find and the page's own /; Search Notes goes to All Notes to search. The app hides the page's heading and search box as it loads, since the toolbar gives it both, and runs under the toolbar with the window's background through, so the file itself is never adapted. View > Back and Forward (⌘[ and ⌘]) move through the types it has shown. The page fetches nothing, moves only between its own sections, and opens a web link in the browser.
- **Web views: `WKWebView`, not SwiftUI's `WebView`.** The editor and any HTML page use AppKit's `WKWebView` in an `NSViewRepresentable`, as the established Mac apps built this way do (MarkEdit, NetNewsWire). SwiftUI's `WebView` and `WebPage` (macOS 26) suit showing web content, but an editor needs what they do not offer: printing (Apple DTS: not supported), filtering WebKit's context menu rather than replacing it, routing undo and ⌘Z to the page's own history, dropped files and focus. Their soft toolbar edge is testing-only SPI even in Apple's own sample, so they offer no public way to it either. Revisit when Apple makes editing, printing and the scroll edge public. Two WebKit settings used here are not public API, as Apple's own `WebView` uses them: a clear background and the soft edge under the toolbar. Each is set only while WebKit answers to it (`WebViewChrome.swift`); without them the page keeps its own background and stops below the toolbar.
- Notes are held byte for byte. A note opened and left alone is never rewritten; an edited note keeps the text of every block the edit did not reach, and only edited or new blocks take the editor's canonical form (`editor/src/preserve.ts`). The app keeps each file's envelope, its front matter, byte-order mark and Windows line endings (`MAPP/Model/NoteFile.swift`), and the page only ever sees the body; link definitions are kept by the page. `editor/fixtures/corpus/` holds notes in unusual but valid markdown, each with one paragraph marked for the tests to edit; add a fixture for any form found to be rewritten.

## Storage and Marfa

- Notes are `.md` files in the folder the person picks; each directory at the top of it is a folder, and the files at the top are the Inbox. Anything whose name starts with a dot, such as Marfa's `.marfa`, and the `Attachments` folder are not notes. The folder is remembered as a security-scoped bookmark.
- The folder is shaped so Marfa's folder device can sync it. Front matter is found by Marfa's rule (`NoteFile.frontMatterLength`); a note's title is its `title` property, otherwise its file name; a favorite is Marfa's ordinary `favorite` tag in the `tags` field, read by Marfa's own rule (a list, tags separated by commas, or nothing; `NoteFile.tags`) and changed in the form already there (`NoteFile.setFavorite`), which reads its result again and refuses tags Marfa cannot read or an edit that would change anything but that one tag, and the person is told; every other property, `marfa_id` among them, is kept as written. Front matter is edited line by line and never re-emitted.
- `NoteStore` is where notes are kept, in Marfa's words (trash, restore, purge). `FolderStore` keeps them as files and keeps the trash in the app's own storage, since a file moved within the folder reads to Marfa as a rename. Each item's identifier is kept beside the trash too (`IdentityLedger`): an item is known again by its file's identity, then by its path, so it keeps its identifier across launches and renames, those made while the app is closed among them, and a copy is a new item. A lost ledger is made again from the folder, which changes the identifiers once. Windows, what they show and select, and dragged notes name items by this identifier, never by path, so a lost ledger costs only what windows restore. Folder order is still kept by name. A Marfa store is meant to take over the trash, restore and purge; conflicts between writers are Marfa's to settle, not the app's.
- `NoteLibrary` decides every path and hands the store one change at a time, which the store makes in order off the main thread, coordinated and whole. New Item keeps an in-window draft until the person enters the content area or submits the title. Creation then writes the chosen title, type and parent through the same store; later body edits are saved by the editor.
- A note's file is named after its first line as it reads (`NoteText.name(for:)`, the one place a name is made safe), and follows the line while the note goes by it: once the person leaves a note whose first line changed, the file is renamed, so Marfa sees one rename rather than one per word. A name given with Rename Note that is not the line's stops the following. A first line with characters a file name cannot hold is also kept whole as the note's `title`.
- A Marfa library is read through the `Marfa` package's working copy (`MAPP/Model/Marfa/`). `MarfaSource` is its `ItemSource`: the copy answers every read, so it paints before and without the network, and writes go to the copy's queue at once. `MarfaEngine` is the one place the source changes what it holds; `MarfaSync` does all the server work (hydrate, catch up, drain, change of key) beside it. Each server address has its own copy in the app's own storage (`MarfaStoreLocation`), never inside a notes folder.
- `MarfaHost` owns the connection: the address in defaults and the key in the keychain (`KeychainKeyStore`). A launch opens the saved copy and paints from it before asking the server. Leaving a copy, by disconnecting or changing the address, never drops writes silently: while any wait or were refused, the person chooses to keep the copy, which connecting the same address again resumes, or to discard it. A refused key parks the queue until Settings gives another, and the parked writes go with the next drain. Tests use `MemoryKeyStore` and a temporary store location, never the keychain or the default location.
- `SyncReporting` (`MAPP/Model/Items/`) says what a source has yet to send and lists each problem: a write refused, blocked or dead, or a conflicted copy, found by its `conflicted-copy` tag. Each carries the person's content as plain text and only the actions the contract allows (`MarfaProblems`); a refused write stays listed until it is discarded. The model gives states and counts; the app owns their wording.
- Debug builds launched with `-MAPPSampleFolder` open a fresh folder of sample notes in the app's own storage; the UI tests use it.

## Releases

- Builds reach TestFlight through Xcode Cloud: a workflow started by a tag beginning with `v` archives the app and gives it to internal testers. There is no other distribution, so no Sparkle and no notarization.
- To release, an agent tags the merged commit on `main` with the next version (see Versions) and pushes the tag. Agents cannot see Xcode Cloud, so the release is checked in App Store Connect: the build for the tag's version appears under TestFlight.
- `ci_scripts/ci_post_clone.sh` runs in the cloud checkout: it writes `Config/Local.xcconfig` from the workflow's secret `MAPP_DEVELOPMENT_TEAM`, and sets `MARKETING_VERSION` from the tag (`1.2.3` or `v1.2.3`) in that copy only. Xcode Cloud numbers the builds. The repository still never holds a team or a version.

## Commands

- `xcodebuild -project MAPP.xcodeproj -scheme MAPP -destination 'platform=macOS' -derivedDataPath build test` builds and runs every test. The UI tests take control of the keyboard and mouse; add `-only-testing:MAPPTests` for the unit tests alone.
- The built app is `build/Build/Products/Debug/MAPP.app`.
- In `editor/`: `pnpm install`, then `pnpm test` (the editor's own tests, in jsdom), `pnpm typecheck` and `pnpm build`. `MAPPTests/EditorTests.swift` runs the built page in real WebKit through the app's bridge.
