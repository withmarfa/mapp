# MAPP

This file governs every session that works in this repository.

## What this repository is

MAPP: a native macOS markdown notes app with a sidebar, a list and a page, in the manner of Notes and Mail. SwiftUI throughout, AppKit only where SwiftUI cannot express something. Notes are markdown files in a folder the person chooses.

## Conventions

- **American English** in code, comments, commits and repository files.
- **Scoped Conventional Commits**, for example `feat(app):`, `fix(editor):`, `test(model):`. Present tense, lowercase, short.
- **Branches and pull requests.** Work goes on a branch and reaches `main` through a pull request, squash-merged once the tests pass and a reviewer has read it. There is no CI; the tests are run locally before merging. Once the work is merged, bring the local `main` up to date (`git pull --ff-only` on `main`) so the next piece of work starts from it.
- **Comments explain why, not what.** A comment survives only if it carries a reason the code cannot.
- **No personal detail.** No absolute paths, machine names, account names or credentials in any file here.
- **No legacy.** No compatibility shims, deprecation aliases or migration paths. Removed means gone.
- **No time estimates.**

## Platform

- macOS 27 and Xcode 27 only. No `#available` checks and no fallbacks for earlier systems.
- Swift 6 language mode, main-actor isolation by default, Swift Testing.
- Native containers and controls (`NavigationSplitView`, `List`, toolbars, commands, system materials) so the system supplies the look. Custom chrome needs a reason. Check API and design questions against Apple's documentation and the Human Interface Guidelines, not memory.
- **Aesthetic.** The app should feel like the Codex app or Craft Docs: Apple's system components, done nicely and customised with care, not a web app's chrome. The Liquid Glass toolbar buttons, the sidebar and the split view stay the system's; what the app adds (the palette, the column search, the page) is drawn to sit beside them as if it were theirs.
- The toolbar over an item (`MAPP/Views/NoteToolbar.swift`) has one trailing group: New Item (plus), Format (Aa), Details (information circle), and More. Format includes lists and table insertion; More includes Share and Add Attachment, which opens the existing image attachment chooser. Once the page header scrolls away, the item's title appears at the leading edge. The title and New Item stay fixed; the other toolbar items are customizable, and every action is also a menu command, since a toolbar can be hidden or changed. The command palette on ⌘K (`MAPP/Views/CommandPalette.swift`) offers the same commands, the sidebar's places and the notes and files by title, and lists only what could be done at that moment. Search lives in the list's column, as Mail's does: a button beside Sort becomes a field across the column (`MAPP/Views/ColumnSearch.swift`, the system search field, since SwiftUI's own search goes to the window's end), which ⌥⌘F opens. Its native close-button accessory remains visible even when the field is empty, because closing search also restores the column's toolbar. ⌘P opens the palette searching the text of every note and the name of every file. ⇧⌘P prints, since ⌘P is search.
- App Sandbox and hardened runtime stay on. The sandbox allows outgoing connections only because WebKit's page process needs them; the page itself loads nothing but the files its note embeds, from the app. Every user-facing string goes through the String Catalog.
- A checkout builds without a developer account and signs to run locally. `Config/Signing.xcconfig`, the project's base configuration, leaves the team empty and includes the ignored `Config/Local.xcconfig`, which `aic-infisical-run -- scripts/render-local-signing.sh` writes from Infisical to sign with the team. Never commit a team identifier or edit the rendered file by hand.

## Versions

- A version exists only as a git tag: `v` followed by the version, such as `v0.0.5`. Agents create the tag when a release is called.
- Every version is `0.0.x` until the first public release, because WithMarfa keeps every version inside its code at 0 until then. Each release is the latest tag plus `0.0.1`, so `v0.0.5` follows `v0.0.4`.
- Agents never write a version into a file: `MARKETING_VERSION` stays `0.0.0` in the repository, since `ci_scripts/ci_post_clone.sh` sets it from the tag in the cloud copy only.

## Layout

- `MAPP.xcodeproj` is a native Xcode project whose `MAPP/`, `MAPPTests/` and `MAPPUITests/` groups follow the folders on disk; add files by creating them, not by editing the project file. The bundle identifier and display name live in the target's build settings. `MAPP/Info.plist` holds only what build settings cannot express (the note drag type) and is excluded from the app's resources.
- `MAPP/Model/` holds the notes model, free of SwiftUI; `MAPP/Views/` the windows and panes; `MAPP/AppIcon.icon` is the Icon Composer app icon. `MAPPTests/` holds the Swift Testing unit tests, hosted in the app; `MAPPUITests/` the XCTest UI tests that drive the running app through its accessibility tree. `Design/` holds artwork that is not built into the app.
- `MAPP/Localizable.xcstrings` is kept in sync by building in Xcode; `xcodebuild` alone does not update it.
- `editor/` is the note editor: Milkdown on ProseMirror in TypeScript, built by Vite into one self-contained page, `MAPP/Editor/Page/editor.html`, which is committed so the app builds without Node. After changing anything in `editor/`, run `pnpm build` there and commit the page with the change. `MAPP/Editor/` holds the Swift side: the web view, the controller that drives the page, and the bridge's messages. The page fetches nothing from the network and never navigates. A file a note embeds, by `![](path)` or `![[file]]` (`![[file|400]]`), shows by what it is: an image, sound or video with WebKit's controls, a PDF in a frame, anything else as a card that opens it on click; the context menu over any of them adds Show in Finder, and Open for a document. Open never hands over a file that might run (a program, a script, a web page, a link file, anything marked executable or of a kind it cannot tell); such a file is shown in the Finder instead (`EmbeddedFiles.opens`). The page asks the app what each embed is through the `embeds` message, and loads it only through the app's `mapp-embed:` scheme (`MAPP/Editor/EmbeddedFiles.swift`), which streams the file from disk in pieces and answers ranges; the page's Content-Security-Policy allows that scheme only for images, media and frames. `ItemLibrary.embeddedFile(_:in:)` is the one place an embed becomes a file: it reads the path or name as Marfa's core does (relative to the note, `/` from the folder's root, a name nearest the note first, without regard to case), and only a regular file inside the notes folder, reached without a symbolic link or a hidden name, is served. The file is opened through no symbolic link and kept only if the opened descriptor's own path is inside the folder (`OpenFile`), and everything the page is told or served comes from that descriptor, so a folder changed after the path was found cannot put another file behind it. An embed of a document (`.md`, `.markdown`, `.txt`, or a name such as `![[A note]]`), one in code, and a missing file or one outside the folder show as text or as their name. Every embed and `[[link]]` is written back byte for byte (`editor/src/wikiembeds.ts`). An image's width, set by dragging its edge, is kept in its alt text as `![name|400](…)`, or as `![[name|400]]`, as Obsidian reads both. A note's text runs to a reading width, which Settings adjusts, unless Full Width is chosen in the View menu or Settings; the width comes from the page's margins, so a click beside the text still places the caret. Text and reading width use `rem`; the native header's measured height reaches the page in pixels. Printing and Export as PDF print the page itself through WebKit, laid out by its `@media print` styles, which remove the header's reserved space. The native item header overlays the page, whose top padding reserves its measured height. WebKit's scroll offset reaches the native header through the script bridge, so the header scrolls with the body and clips away at the top. `MAPP/Editor/ScrollingHeader.swift` hosts the native controls and forwards their unhandled wheel events to WebKit through the public AppKit responder API, because the sibling views' responder chains do not meet. Opening a note starts at the top without focusing the editor; heading marks and selection outlines appear only while editing. WebKit lets the window background through; the toolbar and find bar have a fixed inset, updated only when layout changes (`MAPP/Editor/WebViewChrome.swift`, `WebViewContainer`). The header is also offset below the find bar.
- Settings (`MAPP/Views/SettingsView.swift`) fills the current main window with a native two-column `NavigationSplitView`: a `.sidebar` List of categories, system `.searchable` sidebar search, a Back toolbar command, and a grouped Form for the selected preferences. The system supplies the sidebar material, row selection, and search layout; a native toolbar item displays the active pane title. The existing three-column workspace stays mounted underneath, preserving the selection, column widths and unsubmitted draft. It is hidden and disabled while Settings is open, its toolbar contributions are suppressed, and its focused command values are cleared. Settings opens through the same presentation from the app menu, ⌘, and the command palette; a request from a note window or with no main window opens a main window. Settings search filters categories by their names and preference labels. Returning restores the retained workspace. Changing the notes folder flushes the open editors before choosing the new library, and a Marfa pane connects the app to a Marfa server.
- `MAPP/Types/` holds Marfa Types, the item types and edge types of the library's catalogue, shown with native views. It sits with Recently Deleted at the foot of the sidebar, below however many folders there are (a second list, sized to its rows, so the arrow keys do not cross into it; ⌘K reaches both). `TypeDetails` works out what each type shows from the catalogue, `TypesBrowser` holds what a window has open, and `TypesListView` and `TypeDetailView` lay it out in SwiftUI. Picked, it keeps the window's three columns: the list of types, as a tree of parent types that searching opens throughout and flattens, where the note list goes, and the chosen type where the note goes. The window never changes its columns, since AppKit crashed laying out the toolbar as the columns changed with the sidebar hidden or resized. The list column's search there searches the types rather than the notes, as does Find; Return opens the first match, and Search Notes goes to All Notes to search. Each window keeps its own `TypesBrowser` (`Browser.types`), so a type chosen stays chosen while other places are shown. View > Back and Forward (⌘[ and ⌘]) move through the types it has shown. A link between types chooses the type it names.
- **Web views: `WKWebView`, not SwiftUI's `WebView`.** The editor uses AppKit's `WKWebView` in an `NSViewRepresentable`, as the established Mac apps built this way do (MarkEdit, NetNewsWire). SwiftUI's `WebView` and `WebPage` (macOS 26) suit showing web content, but an editor needs what they do not offer: printing (Apple DTS: not supported), filtering WebKit's context menu rather than replacing it, routing undo and ⌘Z to the page's own history, dropped files and focus. Their soft toolbar edge is testing-only SPI even in Apple's own sample, so they offer no public way to it either. Revisit when Apple makes editing, printing and the scroll edge public. Two WebKit settings used here are not public API, as Apple's own `WebView` uses them: a clear background and the soft edge under the toolbar. Each is set only while WebKit answers to it (`WebViewChrome.swift`); without them the page keeps its own background and stops below the toolbar.
- Notes are held byte for byte. A note opened and left alone is never rewritten; an edited note keeps the text of every block the edit did not reach, and only edited or new blocks take the editor's canonical form (`editor/src/preserve.ts`). The app keeps each file's envelope, its front matter, byte-order mark and Windows line endings (`MAPP/Model/NoteFile.swift`), and the page only ever sees the body; link definitions are kept by the page. `editor/fixtures/corpus/` holds notes in unusual but valid markdown, each with one paragraph marked for the tests to edit; add a fixture for any form found to be rewritten.

## Storage and Marfa

- Notes are `.md` files in the folder the person picks; each directory at the top of it is a folder, and the files at the top are the Inbox. Anything whose name starts with a dot, such as Marfa's `.marfa`, and the `Attachments` folder are not notes. The folder is remembered as a security-scoped bookmark.
- The folder is shaped so Marfa's folder device can sync it. Front matter is found by Marfa's rule (`NoteFile.frontMatterLength`); a note's title is its `title` property, otherwise its file name; a favorite is Marfa's ordinary `favorite` tag in the `tags` field, read by Marfa's own rule (a list, tags separated by commas, or nothing; `NoteFile.tags`) and changed in the form already there (`NoteFile.setFavorite`), which reads its result again and refuses tags Marfa cannot read or an edit that would change anything but that one tag, and the person is told; every other property, `marfa_id` among them, is kept as written. Front matter is edited line by line and never re-emitted.
- `NoteStore` is where notes are kept, in Marfa's words (trash, restore, purge). `FolderStore` keeps them as files and keeps the trash in the app's own storage, since a file moved within the folder reads to Marfa as a rename. Each item's identifier is kept beside the trash too (`IdentityLedger`): an item is known again by its file's identity, then by its path, so it keeps its identifier across launches and renames, those made while the app is closed among them, and a copy is a new item. A lost ledger is made again from the folder, which changes the identifiers once. Windows, what they show and select, and dragged notes name items by this identifier, never by path, so a lost ledger costs only what windows restore. Folder order is still kept by name. A Marfa library keeps the bin, restore and purge with the server (`MarfaLibrary`, below); conflicts between writers are Marfa's to settle, not the app's.
- The views, the commands and the editor reach a library only through `ItemLibrary` (`MAPP/Model/Items/ItemLibrary.swift`), read from the environment's `library` value, so none of them knows which kind of library is open. `NoteLibrary` is the files library; `MarfaLibrary` is the Marfa library. What only files have, such as a file's URL or the folder a note's links resolve in, answers nil in a library without files, and a write a library cannot make is left out of its `capabilities`, so the views dim or hide the command and refuse the drop: moving, erasing for good, renaming a file, editing folders and importing files each have one. Rename Note names a note's file, which only files have; a title is a property, which any library edits. `FakeItemLibrary` in the tests holds items in memory, for testing the views' models without a folder.
- `NoteLibrary` decides every path and hands the store one change at a time, which the store makes in order off the main thread, coordinated and whole. New Item keeps an in-window draft until the person enters the content area or submits the title. Creation then writes the chosen title, type and parent through the same store; later body edits are saved by the editor. An edit typed on text the note no longer holds, as when another app or window changed it while the person typed, is kept beside the note as `<name> (Conflicted Copy).md` rather than written over that change, and the person is told.
- A note's file is named after its first line as it reads (`NoteText.name(for:)`, the one place a name is made safe), and follows the line while the note goes by it: once the person leaves a note whose first line changed, the file is renamed, so Marfa sees one rename rather than one per word. A name given with Rename Note that is not the line's stops the following. A first line with characters a file name cannot hold is also kept whole as the note's `title`.
- A Marfa library is read through the `Marfa` package's working copy (`MAPP/Model/Marfa/`). `MarfaSource` is its `ItemSource`: the copy answers every read, so it paints before and without the network, and writes go to the copy's queue at once. `MarfaEngine` is the one place the source changes what it holds; `MarfaSync` does all the server work (hydrate, catch up, drain, reading the bin, change of key) beside it. The copy holds both tiers (`hydrate(types:tier: .all)`), so the Inbox and the rest of the library read from one copy, offline too; a copy made for one tier takes the other at its next refresh. The package's typed events tell the engine when the server goes away and comes back (`serverUnreachable`, `serverReachable`), and an item's properties keep the order the server gives them (`JSONObject`). A source move the server accepts, like a retype, expires the copy as the drain answers it (`copyExpired` with `read_view_changed`), and the drain throws without its report. `MarfaSync` then hydrates again, which keeps the queue, so nothing queued is lost, and only then reads the answers from the queue, where they are already recorded, and tells the engine as it would a report, so the person's write is answered: the engine reads the changed items again, which an expired copy refuses. The drain stops at the write that expired the copy, so each such answer costs one hydration, and several children chosen at once under a new parent hydrate once each. The engine reloads what the copy holds and publishes only what differs, so a window keeps its selection and place. Each server address has its own copy in the app's own storage (`MarfaStoreLocation`), never inside a notes folder.
- `MarfaHost` owns the connection: the address in defaults and the key in the keychain (`KeychainKeyStore`). The app makes one at launch (`Libraries`, below) and Settings connects it. A launch opens the saved copy and paints from it before asking the server. Leaving a copy, by disconnecting or changing the address, never drops writes silently: the copy reads its own queue for what waits or was refused, after the writes already submitted are queued and in the same step as it closes, and while any do the person chooses to keep the copy, which connecting the same address again resumes, or to discard it. A discard names the writes the person was shown, so one that lands after, such as a late save, keeps the copy and the person is asked again. A discarded copy is marked before anything is removed and is never opened again as it was. Disconnecting forgets the address before it removes the key and the copy, so a quit part way never opens that server again at the next launch; switching server shows the new server's library before the old key and copy are removed. A refused key parks the queue until Settings gives another, and the parked writes go with the next drain; a key that works is kept until the server has taken the new one. Writes made while the key changes wait for the copy rather than fail. Tests keep keys in memory and use a temporary store location, never the keychain or the default location.
- `MarfaLibrary` (`MAPP/Model/Marfa/`) is the `ItemLibrary` over a connected source, which `Libraries` chooses whenever the host's copy is open. It holds what the source last said, in one observed record per item and an index of places and edges (`MarfaItemIndex`), so a read costs what it returns, and it changes nothing itself: every write goes to the source, which applies it to its copy at once. A write that reaches a source after it closed is kept nowhere, so the source refuses it and the person is told (`MarfaEngine.notKept`). It reads every body as it loads, so the editor has text at once, and holds the text the person typed until the source answers it, since a read that raced the write would be older. Every save names the version of the text it was typed on, which the editor keeps for each load (`EditorController`). Only the first save typed on a version is merged against it (`BodyMerge.asRead`); later ones follow the person's own (`.following`), which the engine sends on the version the person's own answered writes account for: laid over them while the copy holds nothing else, and merged against that version once another device's change has come in. An answer is counted toward that version only once the version it needs can be read, and stays in the queue until then. So a person's saves never conflict with each other, and never overwrite text they did not see. Text typed before the page took in newer text, and reported after the reload, is sent as typed on the older version, so the server keeps both, and the page keeps the newer text. The page follows `body(of:)` as well as the version, so where the server keeps its own text over the person's, the page shows the server's and says their changes went to a copy. The Inbox is the feed tier; All Items is every active item in either tier, files among them; a type's place holds its subtypes; a project holds everything below it through `parent-of`. Relationships are edges, named as the end that holds them writes them (`child-of`), with the other end's as `inverse:` and the edge type; links are checked against the catalogue's types, roles, how many each end may hold and the contract's cycle rule before they are sent. A link is added or removed in one write. An end that holds one link of its type has it replaced by moving the edge's other end (`edges.update` with an `EdgeEdit` that names the end), one queued write that keeps the edge's id, so a new parent for an item is one move: the end that stays never holds none or two, and a refusal leaves the old link. A move also takes an item whose own link points elsewhere, such as a child chosen under a project from the project's side. A link a third item holds as its own, such as one where another item already supersedes the item chosen, is never taken from it: the person is told which item holds it. A move to the end the edge already holds, as an undo after a refused move makes, is answered at once and queues nothing, since the server refuses an update that changes nothing. Only one end moves, so a change that would need two edges to change, where both ends already hold one, is told and not sent. The pre-checks keep to `edges.md` and the package: an end that stays holds one (otherwise `validation_error`), a self-loop is `edge_cycle`, and a cycle is judged without the edge being moved. What the copy cannot judge, such as a longer cycle or a new end the server does not hold, is queued and refused by the server in its own words, and the edge returns to where it was. Where a field that holds many takes one item in place of another, the new links go first and the old ones are removed only once the source has taken them, so a refusal never leaves neither. Search is the copy's; one that fails keeps what was found and says why. Undo registers the writes that put back what changed, made at the version current when it runs.

  What an item's text links or embeds is written as edges by the package as the text is saved, and read back by it (`Items.links(in:)`): a `[[link]]` is a `references` edge, shown at its target as Linked From and in the inspector as Links in Content, and an embedded file is an `attached-to` edge from the file to the item, shown as Attachments. The engine asks for an item's links only where its text has a `[[` or an `![`, and again after a drain, a catch-up or a change from another device, since a name the copy could not resolve is `pending` until the server answers; a link that names no item, more than one, or none yet is an edge of the item with that target, never a guess. A link is changed in the text, not as a relationship. Add Attachment and pasted images go through the package's `attach(to:file:)`, which makes the upload, the file item and its edge and names the file the text embeds (`Attached.embed`, `![[name]]`); the page writes that name as a markdown image, `![name](name)` with the name percent-encoded, which the core reads as the same edge, into the note where the caret is, and the editor saves it as it does any typing, which is why the package's own `embed(file:in:_:)`, which edits the body itself, is not used. A file's name is made different from the item's other attachments first, since an embed must name one file alone. A file item shows its size as `size_bytes`, an integer the package stamps when the file is queued and the server sets from the bytes it holds; anything else is no size.

  The bin is the server's. `MarfaSync` reads it a page at a time when the server is reached, after a refresh and after a delete or restore is answered; the copy lets a deleted item go once the delete is answered, so the engine keeps its last row for Recently Deleted until the bin is read, and a copy that never held the item lists it from the bin, text included. Restoring an item the copy let go of is made by its id and shown nowhere until the server answers, as the package says. Delete Permanently is `purge`, which is never queued: it is offered only while the server can be reached, runs after the writes submitted before it have been sent, goes at the version the person was shown, and is confirmed by the dialog the views already have. The server's answer is the write's verdict, so a refused purge is told to the person in the server's words. Moving, renaming files, folders and importing are a files library's, and say so plainly through `failure`; importing is not offered because the package attaches a file to an item and has no call that makes a file item of its own. A Marfa folder is not MAPP's folder: it is a `system.folder` item holding the settings a device keeps a directory in step with (a saved search, include and ignore patterns, defaults for new files, a removal threshold), and it places no item, where a MAPP folder is a directory a note is moved into. So the package's folder calls (`items.folder`, `list(inFolder:)`, `createFolder` and the rest) are not used, `.folders` stays out of a Marfa source's capabilities, and a Marfa library shows no folders. The page does not show a Marfa library's embedded files yet, since `embeddedFile(_:in:)` reads only the notes folder.


- `SyncReporting` (`MAPP/Model/Items/`) says what a source has yet to send and lists each problem: a write refused, blocked or dead, or a conflicted copy, found by its `conflicted-copy` tag and linked to the item it was made from by the package (`Items.original(ofConflictedCopy:)`), read from the copy alone. An original shows the copies the package lists for it (`conflictedCopies(of:)`, the bin left out) as a conflict, so it still does once the verdict that made the copy is forgotten, or offline. Each carries the person's content as plain text and only the actions the contract allows (`MarfaProblems`); a refused write that carried content stays listed until it is discarded, and one that carried none, such as a tag, only while the library stays open. The model gives states and counts; the app owns their wording (`MAPP/Model/Marfa/SyncWording.swift`: state in, words out, so each sentence is tested without a window).

- `Libraries` (`MAPP/Model/Libraries.swift`) is what the app owns: the notes folder, the `MarfaHost` and the library the windows read, which is the host's `MarfaLibrary` while its copy is open and the folder's `NoteLibrary` otherwise. With no server set the folder's library is chosen exactly as before and nothing about Marfa shows anywhere. A server set whose copy is not open (a refused key, a copy that cannot be opened) is never answered with the folder: the window says so and points to Settings, and an item's window restored while the copy opens waits rather than closes. When a Marfa library is open no notes folder is needed or asked for. Before the host changes which library the windows read, and before the app quits, every open page hands over its last edit and each library keeps its writes on this Mac (`Libraries.flushEditors`): the folder's on disk, and a Marfa library's in its copy's queue (`ItemSource.queueSubmitted`), never waiting on the server, so quitting offline is not held up. Quitting waits for this for a few seconds at most. While the host closes a copy to open it again, as when a key is replaced, the windows wait rather than show the notes folder. A main window's `Browser` belongs to `RootView`, above the library, so a change of library starts the window afresh (`Browser.adopt`: selection, place, search, renaming and the window's undo are dropped, since they name or act on items the other library may not have; the page restores only what still exists) while a draft the person was writing is kept, less a parent the new library lacks. A draft whose item the library left already holds is not kept, since its text is there; one refused, or not yet answered, is kept, since no queue may hold it. An item's window clears its undo when its page goes. The unit tests hosted in the app and the UI tests run on an in-memory key store and a temporary store location, never the person's keychain or saved server.
- Settings has a Marfa pane (`MAPP/Views/MarfaSettingsView.swift`, over `MarfaSettingsModel`): the address, the key in a secure field that is kept in the keychain by the host and never shown again, Connect and Disconnect, and the connection in words (`ConnectionStatus`). A refused key shows as "Key refused" with a field for a new one (`replaceKey`), which hands over the pages' edits first, since a copy that cannot take the key is closed and opened again. Once the host holds a key, the pane forgets what was typed, a switch done but for removing the old server's key or copy among them, and that is told as a switch, not a disconnect. Each `MarfaHost.Problem` is told as what happened and what to do (`MarfaSettingsModel.notice(for:)`), never as the error. Leaving a copy, by disconnecting or switching server, while changes wait asks the person to keep the copy or discard it, shows the text of each change that carried text (`UnsentWrites.texts`, read from the queue in the same step as the count) and how many more could not be shown, and passes exactly those changes to `disconnect(.discardCopy(...))`; one that arrives after is asked about again, and cancelling or leaving Settings changes nothing.
- The window says nothing while everything is in step or while the app reads a folder. Otherwise one quiet line at the foot of the sidebar (`SyncStatusBar`) says the most important of: key refused, library unavailable, changes that need attention, offline, catching up, or sending changes still waiting after a few seconds, and opens a popover with the connection and each change that needs the person (`ProblemWording`): the text it carried, Copy Text, and only the actions the contract allows for it (Discard, Try Again, Undo Change, Keep Copy, Discard Copy). Discarding a change that carried text is confirmed, since the change holds the only copy. A conflicted copy is shown with its original, and opens in a window of its own.
- A new item in a Marfa library is shown when its source says so, not when the create is queued. `Browser.createDraft` keeps the draft on the page, as typed and not editable, until `finishCreation` finds the item, then hands over to it; a second Return makes nothing more, and a refused create gives the draft back to edit and send again while the library says why: one refused once queued is also listed with its text, and one refused before it was queued (`ItemLibrary.wasRefused(creating:)`), as while the copy is brought up to date, is held only by the draft.
- A file item's file is fetched where the library does not have it at hand (`ItemFileView`, `ItemFileResolution`); each load names its item and only the latest is shown (`ItemFileLoader`), so a slow answer never shows or shares under another item; a library without files answers nil, and Share, Show in Finder and Open stay off. `Browser.fileFetched` gives the commands the location of a file fetched to show.
- Debug builds launched with `-MAPPSampleFolder` open a fresh folder of sample notes in the app's own storage; the UI tests use it.

## Releases

- Builds reach TestFlight through Xcode Cloud: a workflow started by a tag beginning with `v` archives the app and gives it to internal testers. There is no other distribution, so no Sparkle and no notarization.
- To release, an agent tags the merged commit on `main` with the next version (see Versions) and pushes the tag. Agents cannot see Xcode Cloud, so the release is checked in App Store Connect: the build for the tag's version appears under TestFlight.
- `ci_scripts/ci_post_clone.sh` runs in the cloud checkout: it writes `Config/Local.xcconfig` from the workflow's secret `MAPP_DEVELOPMENT_TEAM`, and sets `MARKETING_VERSION` from the tag (`1.2.3` or `v1.2.3`) in that copy only. Xcode Cloud numbers the builds. The repository still never holds a team or a version.

## Commands

- `xcodebuild -project MAPP.xcodeproj -scheme MAPP -destination 'platform=macOS' -derivedDataPath build test` builds and runs every test. The UI tests take control of the keyboard and mouse; add `-only-testing:MAPPTests` for the unit tests alone.
- The built app is `build/Build/Products/Debug/MAPP.app`.
- In `editor/`: `pnpm install`, then `pnpm test` (the editor's own tests, in jsdom), `pnpm typecheck` and `pnpm build`. `MAPPTests/EditorTests.swift` runs the built page in real WebKit through the app's bridge.
